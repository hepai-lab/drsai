# 广场-智能体「官方平台智能体」输出渲染差异分析与远程输出优化策略

> 分析对象：`apps/desktop` 左侧栏「广场-智能体」中的**官方平台智能体**（`catalogGroup: "official"`，`source: "remote"`）
> 结论先行：**平台智能体与本地智能体走的是两套完全不同的输出协议与渲染管线**。本地走 OAEP 结构化事件流 → 富渲染；平台走 OpenAI 兼容 `chat/completions` SSE → 仅纯文本 chunk。这就是「输出渲染不同」的根因。

---

## 一、两条输出链路对比

### 1.1 本地智能体（走 `runRuntimeBackendChat`）

```
Runtime (Gateway/OAEP)
  └─ subscribeOaepSession → OaepEvent
        └─ emitRuntimeOaepEvent()  [chat.ts]
              └─ mapRuntimeOaepEvent()
                    ├─ type:"oaep"       → oaepEvent 原始事件
                    └─ projectOaepEventForPresentation()  [oaepPresentationProjector.ts]
                          └─ type:"structured" → StructuredConversationEvent
                                (turn.started / part.started / part.delta /
                                 part.completed / activity.updated / turn.completed …)
```

渲染侧：`useDesktopChatAdapter` 消费 `structured` 事件 → `applyStructuredEventToMessage` 累积 `structuredTurn` → `StructuredMessageParts` 富渲染：

- markdown 正文分块流式渲染（`ChatMessageContent`，含 32KB 虚拟化分块）
- reasoning 折叠区
- progress / subtask 计划进度
- artifact 卡片（可打开、可下载）
- citation 引用与来源面板
- tool / activity 时间线、file_change 文件事件
- interaction（审批 / 输入请求）
- turn.completed 携带 `meta`（backend、workspaceLabel、durationMs）

### 1.2 官方平台智能体（走 `getPlatformAgentChatUrl` + `readSse`）

```
fetch(`${baseUrl}/chat/completions`, { stream:true, model: platformId })
  └─ response.body (SSE)
        └─ readSse()  [chat.ts]
              ├─ parseStructuredConversationSseFrame → (平台一般不返回)
              ├─ parseAgentLogSseFrame              → type:"status"
              ├─ parseAgentInputRequestSseFrame     → type:"input_request"
              ├─ parseChatReasoningSseFrame         → type:"reasoning"
              ├─ parseChatSseErrorFrame             → 抛错
              ├─ parseAgentRunSseFileEvents         → type:"tool_timeline"
              └─ parseChatSseFrame                  → type:"chunk"（纯文本增量）
        └─ 结束：emit(type:"done")
```

渲染侧：只有 `chunk` / `reasoning` / `status`；**没有 structured 事件**，因此拿不到 `structuredTurn`，退化为「纯文本气泡」。平台 run 在 `chat.ts` 里是独立分支（`platformDescriptor` 分支），根本不进入 `projectOaepEventForPresentation`。

### 1.3 关键差异表

| 维度 | 本地智能体 | 官方平台智能体 |
|---|---|---|
| 协议 | OAEP 结构化会话流 | OpenAI 兼容 chat/completions SSE |
| 主事件类型 | `oaep` + `structured` | `chunk` / `reasoning` / `status` |
| 富组件（artifact/citation/tool/plan） | ✅ | ❌ 全部缺失 |
| 流式渲染管线 | 结构化 part 流 + 虚拟化分块 | 仅 `streamingDisplayBuffer` 纯文本 |
| 终态 | `turn.completed`（含 meta/duration） | `done`（无 meta） |
| 恢复/续传 | OAEP 事件重放 + outbox | 仅 `resumeState.content` 字符串续接 |
| 消息持久化 | Runtime 会话 Item | 仅本地 thread 快照 |

## 二、根因定位（按影响面排序）

### 根因 A：平台分支未接入结构化投影管线（核心）
`chat.ts` 中平台分支的 `send()` 直接调用 `readSse()`，而 `readSse()` 只做**帧级解析 → chunk 事件**，从不调用 `projectOaepEventForPresentation` 或 `applyStructuredConversationEvent`。因此无论上游返回多丰富的内容，下游渲染一律降级为纯文本。

### 根因 B：平台 catalog 未声明 / 未使用结构化能力
`hostedAgentCatalog.ts` 里 `capabilities: ["chat","streaming"]` 是**硬编码**（`fetchDdfAgentsLikeWebUi` 与 `normalizeHostedAgent` 均写死）。即使 DDF worker 支持结构化输出，UI 也无法得知，`isPlatformAgentExecutionAvailable` 只校验 `chat` + `streaming`。

### 根因 C：SSE 帧判别顺序对平台不友好
`readSse` 的帧解析是「依次 try 各 parser」。平台若返回非标准帧（如裸 JSON、`data:` 内含 tool_calls、markdown 分片对象），会落到 `parseChatSseFrame` 兜底成纯文本，丢失结构。

### 根因 D：平台无 tool/file/artifact 事件通道
`getPlatformAgentChatUrl` 指向 `/chat/completions`（OpenAI 兼容），该协议本身**不表达**文件变更、工具调用时间线、artifact。即便解析 `tool_calls`，也没有对应的 `ChatEvent` 语义被发出。

### 根因 E：平台 run 缺少终态元数据
平台分支结束时只 `emit(type:"done")`，不带 `meta`（backend、durationMs）。渲染侧 `formatRunContext` / 运行上下文展示为空白，与本地不一致。

### 根因 F：平台分支绕过附件多模态与资源语义
本地通过 `stageAttachments` 生成 `OaepInputResource`（含 sha256、mime、content dataURL）；平台分支把 `attachments` 原样塞进 body，由远端自行解释，渲染侧没有对应的资源卡片。

## 三、远程智能体输出优化策略

策略分三层：**协议层（让平台能表达结构）→ 传输层（chat.ts 解析与映射）→ 渲染层（复用结构化组件）**。目标：在**不要求远端大改**的前提下，让平台输出的渲染向本地看齐；并允许远端主动升级以获得完全一致的体验。

### 3.1 协议层：定义「远程结构化输出契约」（Remote Structured Output Contract, RSOC）

在不破坏 OpenAI 兼容性的前提下，引入**渐进增强**的约定：

1. **能力协商**：平台 catalog 支持 `capabilities` 返回 `structured` / `tools` / `artifacts` / `citations`。`hostedAgentCatalog.ts` 从 `info.capabilities` 读取（而非硬编码），`isPlatformAgentExecutionAvailable` 按实际能力放开。
2. **SSE 扩展帧**：远端可在标准 `data: {choices:[{delta:{content}}]}` 之外，追加带命名空间的帧：
   - `event: structured` + `data: {type:"part.started"|"part.delta"|"part.completed", part:{...}}`
   - `event: activity` + `data: {kind:"tool"|"file_change", ...}`
   - `event: artifact` + `data: {name, path, mime, size}`
   - `event: turn` + `data: {type:"completed", meta:{backend,durationMs}}`
   命名空间前缀保证老客户端忽略未知帧仍可正常工作。
3. **降级保证**：远端若不实现 RSOC，则一切回落为现有 `content` 纯文本，行为不变（向后兼容）。

### 3.2 传输层：在 `chat.ts` 为平台分支建立「结构化映射器」

新增 `createPlatformPresentationProjection()`（与 `oaepPresentationProjector` 同构），在 `readSse` 中：

1. **帧分派扩展**：在现有 parser 链最前插入 `parsePlatformStructuredFrame` / `parsePlatformActivityFrame` / `parsePlatformArtifactFrame`（放 `sseParser.ts`）。
2. **映射为既有 ChatEvent 语义**：把 RSOC 帧映射为**与本地同名的** `type:"structured"` 事件，复用 `StructuredConversationEvent` 类型（`structuredConversation.ts`）。这样渲染层零改动即可获得富组件。
3. **补齐终态元数据**：平台 run 结束（`done` 或 RSOC `turn`）时，合成 `turn.completed`（`meta.backend = "platform:"+platformId`、`durationMs`、`workspaceLabel`）。
4. **纯文本兼容**：未携带 RSOC 的远端，`content` 增量仍走 `chunk`，由 adapter 在「无 structuredTurn」时使用现有纯文本气泡——**保留当前可用路径**。
5. **附件资源语义对齐**：把平台 attachments 的 name/size/mime 映射为 `notice`/`artifact` 结构化 part，让渲染显示资源卡片而非裸文本。

> 关键点：**不要新建一套平台专属渲染分支**，而是把平台输出「翻译」成本地已有的结构化事件，最大化组件复用、最小化维护面。

### 3.3 渲染层：复用结构化组件 + 少量平台适配

1. 平台 run 在 adapter 中创建 `createStructuredTurnState(requestId)`（与本地一致），使 `StructuredMessageParts` 正常工作。
2. 为平台 turn 增加 **backend 标识徽标**（`meta.backend`），在 `formatBackendLabel` 中识别 `platform:` 前缀显示「远程/平台」标签，并附隐私提示（`AgentSquareView` 已有「内容会发送到其运行服务」文案，应在消息气泡中同样体现）。
3. artifact / citation 卡片复用同一组件；平台缺失时按 `part.kind` 自然不渲染，不会报错。

### 3.4 稳健性与降级矩阵

| 场景 | 行为 |
|---|---|
| 远端支持完整 RSOC | 渲染与本地一致（富组件） |
| 远端仅支持文本 | 回落纯文本气泡（当前行为，不劣化） |
| 远端返回半结构化（有 part 无 artifact） | 按 part 渲染，缺失部分不显示 |
| 远端返回未知帧 | parser 兜底为文本 chunk，并计入 `unknownDeltaKinds` 遥测 |
| 网络中断 | 复用现有 `resumeState` + `Idempotency-Key` 续传；结构化帧按序重放 |

### 3.5 落地步骤（建议顺序）

1. **Step 1（低风险，快速收益）**：`hostedAgentCatalog.ts` 移除 capabilities 硬编码，读取远端能力；`chat.ts` 平台分支合成 `turn.completed`（含 meta）。→ 立刻改善终态展示一致性。
2. **Step 2（核心）**：在 `sseParser.ts` 增加平台结构化帧 parser；`chat.ts` 平台分支接入 `platformPresentationProjection`，将 RSOC 映射为 `structured` 事件。
3. **Step 3（渲染复用）**：adapter 为平台 run 创建 `structuredTurn` 并接 `StructuredMessageParts`；补 backend 徽标与隐私提示。
4. **Step 4（对齐增强）**：附件资源结构化映射、artifact/citation 通道打通。
5. **Step 5（治理）**：为 RSOC 增版本号（`x-opendrsai-structured-version`），纳入协议兼容性测试。

### 3.6 验收标准

- 平台返回 RSOC 时：正文/推理/计划/工具/文件/artifact 渲染与本地**同构**。
- 平台返回纯文本时：与当前渲染**逐字一致**（回归无劣化）。
- 平台 run 具有 `backend`、`durationMs` 元数据。
- 未知帧不导致空白或崩溃，且被计数遥测。

## 五、一句话总结

本地智能体输出经 **OAEP → 结构化投影** 获得富渲染；官方平台智能体输出经 **OpenAI 兼容 SSE → 纯文本 chunk** 被降级。优化方向不是「给平台做一套渲染」，而是**定义远程结构化输出契约（RSOC），在 `chat.ts` 传输层把平台帧翻译成与本地相同的 `structured` 事件**，从而让渲染层零改动地复用富组件，并对不支持 RSOC 的远端保持纯文本兼容降级。
