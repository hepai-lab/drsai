# DrSaiAssistant `_process_model_result` 工具输出 → apps/desktop 分工具渲染优化方案

> **范围**：分析后端 `DrSaiAssistant._process_model_result`（`cores/python/packages/drsai/src/drsai/modules/agents/skills_agent/drsai_assistant.py:2578`）中各工具的产出事件，追踪其在 apps/desktop 的完整渲染路径，给出"分工具优化渲染"的落地处理方案。
>
> **核心结论（一句话）**：后端**六类特殊工具分支**额外产出的富信息（Skill 正文、Todo 清单、定时任务结果、配置变更日志等），要么被**翻译器归档丢弃**（`ToolCallSummaryMessage`），要么在前端被**压成"通用工具卡 + 原始 JSON `<pre>`"**。前端目前只有 `tool` 与 `file_change` 两种活动形态有专门 UI，**唯一按工具名的分支只有 `web_search`**。因此问题不在"事件没传"，而在"缺少按工具分派的语义与组件"。
>
> 本轮**只产出分析与处理方案文档**，不修改任何代码。

---

## 一、后端现状：`_process_model_result` 产出了什么

`_process_model_result`（`drsai_assistant.py:2578`）是工具执行分发中心。它**先统一发出两类信号**，再按 `tool_name` 分支执行。

### 1.1 每个 turn 开头必定发出（所有工具共享）

```python
# drsai_assistant.py:2648-2664
tool_call_msg = ToolCallRequestEvent(
    content=original_tool_calls,          # 含全部 tool args
    source=agent_name,
    models_usage=model_result.usage,
    metadata=registry_metadata,           # execution_registry_sha256 / tool_loop_policy_sha256 / tool_policies
)
inner_messages.append(tool_call_msg)
yield tool_call_msg                       # → 前端 tool.start
tools_name = [tool.name for tool in original_tool_calls]
yield AgentLogEvent(
    title="I am using tools: " + " ".join(tools_name),
    source=agent_name,
    content=str(tool_call_msg.content),
    content_type="tools",
    metadata=registry_metadata,
)                                          # → 前端 status.update kind=log
```

### 1.2 六个特殊工具分支 + 一个通用分支

| 分支 | 行号 | 额外 yield 的事件 | 关键 payload | 前端可见性 |
|---|---|---|---|---|
| `Skill` | 2830 | `AgentLogEvent("I am reading skill: X")` + **`ToolCallSummaryMessage`（skill 正文）** | `arguments["skill"]`、skill 全文 | ❌ summary 被归档丢弃 |
| regression tools | 2870 | `AgentLogEvent("Reading regression data")` | 参数 JSON | ⚠️ 仅日志兜底 span |
| `TodoWrite` | 2894 | **`TextMessage(纯文本 todo)`** | `[x]/[>]/[ ]` 文本 | ⚠️ 纯文本，状态语义丢失 |
| `Delegate` | 2932 | **内部 `_execute_subagent` 的 `subagent.*` 事件流** + `Response` | 子智能体输出 | ✅ 走 SubtaskContainer |
| `UpdateUserConfig` | 2973 | `AgentLogEvent("I am updating user's config")` | 变更参数 | ⚠️ 仅日志兜底 span |
| `ScheduledTaskManager` | 2999 | **`TextMessage(result_content)`**（markdown 文本） | create/list/get/delete/toggle 结果 | ⚠️ 文本被丢弃 |
| **通用工具**（else） | 3200 | 无额外 yield；结果走 workbench | `FunctionExecutionResult` | ✅ 进 tool 卡（原始 JSON） |

### 1.3 统一收尾（3236-3319）

```python
# 大输出 → FilesEvent（转 artifact）
if len(encoded_payload) > inline_limit:
    descriptor = await artifact_handler({...}, raw_content.encode("utf-8"))
    yield FilesEvent(source=agent_name, content=FilesContent(...))   # → 前端 artifact part

# 所有结果进 model context（不走 UI）
await model_context.add_message(FunctionExecutionResultMessage(content=exec_results))

# 末尾统一 ToolCallSummaryMessage（"The results of execution: ..."）
yield Response(chat_message=ToolCallSummaryMessage(content="The results of execution:\n "+tool_call_summary+"\n", source=agent_name))
```

> ⚠️ **关键**：末尾这个 `ToolCallSummaryMessage` 已被翻译器**主动归档丢弃**（见 `events/agent_event_translator.py` 中 `ToolCallSummaryMessage` 分支注释 "ARCHIVED"）。因此"执行结果摘要"这段用户完全看不到。

## 二、前端现状：这些事件实际如何渲染

### 2.1 完整链路

```
_process_model_result  yield 事件
        │
        ▼
events/agent_event_translator.py  (autogen 事件 → 语义事件)
   ToolCallRequestEvent    → ("tool.start", {tool_id, name, args})
   ToolCallExecutionEvent  → ("tool.complete", {tool_id, name, args, result, is_error, duration_ms})
   ToolCallSummaryMessage  → (ARCHIVED / 丢弃)
   AgentLogEvent           → ("status.update", {kind:"log", text})   ← 光秃兜底
   TextMessage             → ("message.delta", {text})
        │
        ▼
desktop_gateway/_agent_backend.py:_normalize_event
   tool.start/complete → tool.started/tool.completed (+ operation_ref/call_id)
        │
        ▼
runtime/oaep.py:project_item
   tool → item_type "tool_call"  content={tool_name, call_id, arguments, result, duration_ms}
        │
        ▼
SSE: event: oaep.event  data: {type:"event.item.*", ...}
        │
        ▼
apps/desktop/shared/main/threadRuntimeProjection.ts:361  projectOaepAssistantItem
   tool_call / command_execution → { kind:"tool", toolName, callId, input, output, durationMs }
        │
        ▼
apps/desktop/shared/renderer/src/components/StructuredMessageParts.tsx:862  ActivityTimelineItem
   collapsed: 输入/输出 一行摘要
   expanded : <pre>{JSON.stringify(input,null,2)}</pre> + <pre>{JSON.stringify(output,null,2)}</pre>
```

### 2.2 前端渲染能力清单（已核实）

**`StructuredActivityEvent.kind` 只有 6 种**（`structuredConversation.ts:176`）：
`tool | model | retry | file_change | subtask | log`

**`ActivityTimelineItem`（`StructuredMessageParts.tsx:862`）实际渲染情况**：

| kind | 渲染 | 行 |
|---|---|---|
| `file_change` | 紧凑行：label + `activity.path` 按钮（可打开资源） | 878 |
| `tool` | **最丰富**：状态图标 + `toolName` + label + 时长 + 折叠/展开（input/output 原始 JSON `<pre>`） | 883-917 |
| `model` / `retry` / `subtask`(activity) / `log` | **全部落到同一行 `{label}` 文本兜底**，无任何专门 UI | 919 |

**唯一按工具名的特判**（`structuredProcessPresentation.ts:92-96`）：

```ts
if (activity.kind === "tool") {
  if (activity.toolName === "web_search") return formatWebSearchActivitySummary(activity, language);
  return formatToolActivityLabel(activity.toolName, activity.title, language);   // 通用关键词猜标签
}
```

外加一个检索正则（`StructuredMessageParts.tsx:547`）：`/web[._](search|fetch)/i` → `RetrievalStageSummary`。

**`formatToolActivityLabel`（`structuredProcessPresentation.ts:202`）** 是基于关键词的通用映射（search/read/write/edit/run…→ 中英文动词），**不含任何具体工具名的语义**。

### 2.3 各工具当前观感对照

| 工具 | 前端现在看到 | 问题 |
|---|---|---|
| `Skill` | tool 卡（summary 已被丢弃）→ 工具名 + 原始 JSON | 技能名/正文**全丢**，最严重 |
| `TodoWrite` | tool 卡 + `input` = items 数组原始 JSON | 状态语义（pending/in_progress/completed）丢失 |
| `Delegate` | `subtask.*` → `SubtaskContainer` 富 UI | ✅ 基本可用 |
| `UpdateUserConfig` | tool 卡 + `AgentLogEvent`（光秃 span） | 改了哪些字段看不出 |
| `ScheduledTaskManager` | tool 卡 + 被丢弃的 `TextMessage` | 任务 CRUD 结果看不到 |
| `web_search` / `web_fetch` | ✅ 专门摘要 + 阶段条（`RetrievalStageSummary`） | 已优化 |
| 通用工具（read/write/edit/bash…） | tool 卡 + 原始 JSON | `command_execution` 与 `tool_call` 在 `:361` 被**合并为同一种** |

### 2.4 投影层的既有缺口

- `threadRuntimeProjection.ts:361` 把 `command_execution`（终端命令）与 `tool_call`（结构化工具）**合并成同一种 `kind:"tool"`**，`toolName` 是唯一区分信号。
- `threadRuntimeProjection.ts:404` 把 OAEP `plan` item 的 `steps[]` **直接丢弃**，压成一条 `progress`（与 TodoWrite 渲染同源问题）。
- `aggregateActivities`（`structuredProcessPresentation.ts`）**跳过 `model` 与 `log`**，大量已存在的字段（`usage`、`attempt/limit/errorCode`、`level/content`）被浪费。

## 三、优化处理方案

### 设计原则

1. **在投影层加语义，而非在渲染层硬编码工具名**。前端不应散落 `toolName === "Skill"` 字符串判断（脆弱、易漏）。
2. **渲染层改为"组件映射表"而非 if 链**，`generic` 兜底保持现有行为 → 零回归风险。
3. **能复用的绝不新建**：`Delegate`→`SubtaskContainer`、文件→`file_change` 已有 UI、搜索→`web_search` 已有摘要。

---

### 方案 A（P0）：工具分类字段 + 组件映射表

#### A1. 给 tool activity 增加 `toolCategory`

`apps/desktop/shared/api/structuredConversation.ts:178` 的 tool activity 增加可选判别字段：

```ts
(ActivityEventBase & {
  kind: "tool";
  toolName: string;
  callId: string;
  operationId?: string;
  correlationId?: string;
  runtimeRunId?: string;
  input?: unknown;
  output?: unknown;
  durationMs?: number;
  toolCategory?: "skill" | "todo" | "subagent" | "config" | "schedule"
               | "search" | "file" | "shell" | "generic";   // ← 新增
})
```

由 `threadRuntimeProjection.ts:361` 附近的投影逻辑，按 `tool_name` 映射（与后端六分支一一对应）：

| `tool_name` | `toolCategory` | 目标组件 |
|---|---|---|
| `Skill` | `skill` | `SkillActivityCard` |
| `TodoWrite` | `todo` | `TodoCard` |
| `Delegate` | `subagent` | `SubtaskContainer`（复用） |
| `UpdateUserConfig` | `config` | `ConfigChangeCard` |
| `ScheduledTaskManager` | `schedule` | `ScheduledTaskCard` |
| `web_search` / `web_fetch` | `search` | 现有搜索摘要/阶段条 |
| `command_execution` | `shell` | `CommandActivityCard` |
| 其它 | `generic` | 现有 `<pre>` 实现（兜底） |

#### A2. 渲染层改为组件映射表

`StructuredMessageParts.tsx:883` 的 if 分支内改为：

```tsx
const TOOL_RENDERERS: Record<ToolCategory, React.FC<ToolActivityProps>> = {
  skill:    SkillActivityCard,
  todo:     TodoCard,
  subagent: (p) => <SubtaskContainer ... />,   // 复用
  config:   ConfigChangeCard,
  schedule: ScheduledTaskCard,
  search:   SearchActivityCard,                // 复用现有 web 摘要
  file:     FileChangeActivityCard,            // 复用 file_change 样式
  shell:    CommandActivityCard,
  generic:  GenericToolCard,                   // = 现有 <pre> 行为
};
const Renderer = TOOL_RENDERERS[activity.toolCategory ?? "generic"];
```

**`generic` 完全等价于现有实现**，因此无行为回归。

### 方案 B（P0）：TodoWrite 三态卡片

- 数据来源：`activity.input`（即 `[{content, status}, ...]`），**无需后端改动**即可渲染。
- 三态：`○ 待办(pending)` / `◐ 进行中(in_progress，转圈)` / `✓ 已完成(completed，删除线)`。
- 顶部：进度条 + `n/m`；`output` 中的 `⚠️ Auto-corrected` 前缀渲染为 warning 提示条。
- 解析失败时回退 `GenericToolCard`。
- 中期（方案 D）改为消费 OAEP `plan` item 的 `steps[]`，支持原地 upsert 刷新。

---

### 方案 C（P1）：通用工具拆分 shell / tool_call

- 现状：`threadRuntimeProjection.ts:361` 把 `command_execution` 与 `tool_call` 合并。
- 目标：`shell` → 终端样式（等宽、cwd、exit_code、stdout/stderr_tail）；`tool_call` → 结构化 JSON/字段视图。
- 收益：`bash/read/write/edit` 等不再显示为"原始 JSON"。

---

### 方案 D（P1，需后端配合）：把被丢弃的富信息接回来

| 项 | 后端改动 | 前端收益 |
|---|---|---|
| **Skill** | 恢复 Skill 分支可见性，或把 skill 正文转 artifact | `SkillActivityCard` 显示技能名 + 折叠正文 |
| **ScheduledTaskManager** | 不发 `TextMessage(markdown)`，改发结构化字段（operation + 结果对象） | `ScheduledTaskCard` 表格化任务列表 |
| **UpdateUserConfig** | 在事件里携带变更摘要（字段 old→new） | `ConfigChangeCard` 显示变更 diff |
| **tool.start 日志** | `AgentLogEvent(content_type="tools")` 映射为 activity 更新而非 log | 工具开始即显示语义 |

---

### 方案 E（P2）：补 `model` / `retry` / `log` 兜底

`StructuredMessageParts.tsx:919` 四种 kind 共用光秃 span，可低成本改善（字段均已存在）：

- `model` → token 用量小徽标（`usage`）
- `retry` → 重试进度（`attempt/limit/errorCode`）
- `log` → 可折叠日志行（`level/content`）

## 四、落地优先级

| 优先级 | 内容 | 层 | 成本 | 收益 |
|---|---|---|---|---|
| **P0** | `toolCategory` 字段 + 组件映射表骨架 | 前端 | 小 | 建立分派能力 |
| **P0** | `TodoCard` 三态卡片 | 前端 | 小 | TodoWrite 卡片化 |
| **P0** | `SkillActivityCard` | 前端 | 小 | Skill 恢复正常展示 |
| **P1** | 通用工具拆 `shell` / `tool_call` | 前端 | 小 | 命令类工具可读 |
| **P1** | Skill 正文恢复 / ScheduledTaskManager 结构化（方案 D） | 前后端 | 中 | 信息不再丢失 |
| **P2** | `model`/`retry`/`log` 兜底（方案 E） | 前端 | 小 | 过程信息可视 |

**验收标准**
- `ToolWrite`、`Skill`、`Delegate`、`ScheduledTaskManager`、`UpdateUserConfig` 各自渲染为专用卡片，不再是原始 JSON。
- 未识别工具（`generic`）行为与现状**完全一致**（无回归）。
- `command_execution` 与 `tool_call` 视觉可区分。
- 折叠/展开、时长、错误态在各类卡片中保持一致性。

## 六、一句话总结

`_process_model_result` 对 `Skill/TodoWrite/Delegate/UpdateUserConfig/ScheduledTaskManager/regression` 六类工具都有专门分支并额外产出富事件，但这些信息要么被翻译器**归档丢弃**（`ToolCallSummaryMessage`）、要么在前端被**压成"通用工具卡 + 原始 JSON `<pre>`"**。前端目前仅对 `tool` 与 `file_change` 有专门 UI，且唯一按工具名的分支只有 `web_search`。优化路径是：**在投影层为 tool activity 引入 `toolCategory` 语义，在渲染层改为组件映射表（`generic` 兜底保持现状），并逐步落地 `TodoCard`/`SkillActivityCard`/`ScheduledTaskCard`/`ConfigChangeCard` 等专用卡片；同步让后端把被丢弃的 Skill 正文、定时任务结果、配置变更摘要接回事件流。** 先做 P0 即可把绝大多数工具从"原始 JSON"提升为专用卡片，且不破坏现有行为。
