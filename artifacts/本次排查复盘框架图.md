## 二、三个错误类型

### 错误 A：验证层级错位（最核心）
```
改的是    shared/api/structuredConversation.ts   (源文件)
测的是    shared/test-kit/*.mts                  (直接读源文件)
断言「已修复」
实际运行  windows/out/ 或 Vite dev server        (产物/编译结果)
```
**测试对象 ≠ 运行对象**，中间缺少"运行产物"这一层验证。
Node 侧测试通过 ⇒ 源逻辑正确，**不推出**用户界面已生效。

### 错误 B：把推论当事实（未验证就下结论）
阶段 9 用**构建产物时间戳**推出"用户跑的是旧 bundle"，
但**没先确认该产物是否在运行路径上**。一个未被加载的目录，其时间戳毫无意义。

### 错误 C：混淆"启动模式"与"构建类型"
`windows-desktop-production.cmd` 名字含 "production"，
实际语义是 **Production 端点配置**（HAI 生产地址 / `.drsai-prod` / OIDC-only），
**不是** production build。命名误导 + 未读脚本 = 误判。

## 四、方法教训

| 教训 | 具体化 |
|---|---|
| 验证要落到"用户实际运行的那一层" | 源测试 ✅ → 还需确认 bundle/dev server 是否含改动 |
| 时间戳只有在文件处于运行路径上时才有意义 | 先证明"谁在用这个文件"，再看它的时间戳 |
| 命名不等于语义 | `*-production.cmd` 读脚本再判断，别按名字推断 |
| 结论要匹配证据强度 | "源逻辑正确" ≠ "界面已修复" |
| 主动作废错误推论 | 阶段 9→11 的自我推翻，比坚持错误结论更有价值 |
