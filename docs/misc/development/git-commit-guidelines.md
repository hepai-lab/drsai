# Git 提交与入库初步规范

## 目的

本规范用于判断工作区中的文件是否应进入 OpenDrSai 仓库，并让提交对协作者和未来维护者保持可理解、可复现、可追溯。

## 应提交的内容

- 产品源码、共享协议、构建配置和依赖清单。
- 与行为变更对应的单元测试、集成测试、可复现的验收脚本及其固定测试夹具。
- 由受控生成流程产生、且构建或运行时确实需要的契约代码；应同时保留或说明生成来源。
- 面向项目的设计文档、操作指南、变更说明，以及经过整理的结构化验收记录。

提交前应确认新增脚本具有清晰入口：由构建任务、测试命令、自动化流程或文档明确说明其运行方式与适用场景。

## 不应提交的内容

- 凭据、访问令牌、私钥、会话数据，以及外观类似真实凭据的测试字面量。
- 开发者个人配置、用户目录、设备标识、临时路径和本机诊断快照。
- 可重新生成的构建目录、依赖缓存、日志、性能 trace、安装包、截图、录像及原始设备采集文件。
- 尚未整理或尚未完成的验收过程产物。

这类文件应使用精确的 `.gitignore` 规则排除；不要为了忽略个别产物而把通用源码、测试、文档或资源目录整体排除。

## 文档与验收材料

文档应描述项目可复用的结论、步骤和边界，不应保存个人机器状态或特定运行环境细节。验收材料优先提交小型、结构化、可复核的结果摘要；体积较大或包含敏感上下文的原始媒体、日志和抓取数据保留在受控的外部存储中。

## 提交边界

一个提交应只表达一个完整意图，例如功能、修复、测试补充、文档更新或仓库维护。功能实现与其必要测试可以同提交；无关格式化、依赖升级、生成文件重建和忽略规则调整应单独提交，除非它们是该变更不可分割的一部分。

## 提交前检查

- 检查状态、未跟踪文件和文件体积，确认没有遗漏产物。
- 检查凭据、绝对路径与机器特定信息；测试数据也必须避免触发凭据扫描。
- 运行与改动范围相称的类型检查、测试或验证脚本。
- 确认文本编码与行尾规则一致，避免将纯格式变化混入功能提交。
- 在同步远端分支并解决冲突后，再进行最终提交和推送。

## 判断原则

当一个文件能让其他开发者构建、理解、验证或维护项目时，通常应提交；当它只反映某台机器、某次运行或可由现有源码重新生成时，通常应忽略或移至外部存储。无法明确归类时，优先保留源代码与可复现规则，排除原始运行产物。
