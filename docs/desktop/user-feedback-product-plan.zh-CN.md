# OpenDrSai Desktop 用户反馈功能产品方案

> 状态：P1（一阶段）产品方案初稿  
> 适用范围：`apps/desktop/windows`、`apps/desktop/macos` 与 `apps/desktop/shared`  
> 核心原则：**用户只负责表达不满或想法，App 自动负责还原现场。**

## 1. 背景

OpenDrSai Desktop 需要为用户提供一个低负担的反馈渠道，用来提交：

- App 报错、崩溃、卡死或行为异常；
- 不易使用、结果不符合预期等体验问题；
- 产品意见和改进建议；
- 新功能或新场景需求。

传统反馈表单通常要求用户填写系统版本、App 版本、复现步骤、错误日志和联系方式。这些信息虽然有利于研发定位问题，却显著增加用户负担，并且用户填写的信息常常不完整或不准确。

本方案的目标不是增加一张表单，而是建立一条由 App 自动收集上下文、脱敏和组装证据，用户只需表达主观感受即可完成提交的反馈链路。

## 2. 产品目标与非目标

### 2.1 产品目标

1. 用户能够在 15 秒内完成一次反馈。
2. 明确错误场景尽可能做到一次点击即可提交。
3. App 自动附带足够定位问题的环境和上下文信息。
4. 用户清楚知道将发送什么，并能控制敏感内容是否附带。
5. 每条反馈可以去重、分类、跟进并关联到修复版本。
6. Windows 与 macOS 共用反馈协议、数据模型和主要 UI。

### 2.2 非目标

- 第一阶段不建设完整的客服工单系统。
- 不默认上传用户文件、聊天全文、终端内容或工作区源码。
- 不把用户反馈入口替代为纯后台遥测。
- 不要求用户理解 Runtime、Gateway、Agent、trace 等技术概念。
- 不在第一阶段实现完整的问题录制、远程调试或自动根因分析。

## 3. 设计原则

### 3.1 用户表达感受，系统描述事实

用户最适合回答的是：

- 哪里不好；
- 自己原本想完成什么；
- 希望产品如何改进。

App 应自动回答的是：

- 当时使用的版本、平台和运行环境；
- 哪个模块、任务、Agent 或工具发生了问题；
- 错误前发生了哪些操作；
- 错误码、调用栈、健康状态和关联 ID 是什么。

### 3.2 上下文优先于描述长度

从错误卡片、AI 回复或失败任务上发起的反馈，比从设置页打开的一张空表单更容易定位问题。反馈入口应尽可能靠近问题发生的位置。

### 3.3 默认安全，敏感内容逐项授权

默认诊断摘要必须能够安全提交。截图、对话正文、详细日志、文件信息等内容必须显式展示并允许用户逐项选择。

### 3.4 一次提交不是反馈闭环的终点

提交成功后应返回反馈编号。后续系统需要支持补充信息、合并同类反馈、标记修复版本，以及在用户同意联系时通知处理结果。

## 4. 成熟产品模式参考

### 4.1 VS Code：统一入口与自动填充

VS Code 将核心产品和扩展的问题统一纳入 `Help > Report Issue`，并自动填充环境及相关扩展信息；具体功能也可以接入同一套 issue reporter。

可借鉴点：

- 同一反馈服务支撑全局入口和上下文入口；
- 自动识别问题属于哪个模块；
- 自动附带环境信息，不要求用户手工填写。

参考：<https://code.visualstudio.com/api/get-started/wrapping-up>

### 4.2 Slack：先诊断，再发送报告

Slack 对连接和通知问题提供针对性的诊断流程。普通问题可以在测试结果后直接发送报告；只有复杂、难复现的问题才进入一段时间的网络日志采集。

可借鉴点：

- 针对已知问题先自动运行轻量诊断；
- 普通反馈不要求用户主动找日志；
- 复杂问题再启用有起止边界的复现采集模式。

参考：<https://slack.com/help/articles/205138367-Troubleshoot-connection-issues>

### 4.3 Apple Feedback Assistant：诊断附件与持续跟进

Apple Feedback Assistant 支持附加设备诊断、截图和文件，并允许在反馈提交后继续补充信息或关闭问题。

可借鉴点：

- 诊断信息是结构化附件；
- 用户可以预览和补充；
- 反馈具有持续状态，不是一封不可追踪的邮件。

参考：<https://support.apple.com/guide/feedback-assistant/welcome/mac>

### 4.4 Electron：底层崩溃采集

Electron 的 `crashReporter` 可通过 Crashpad 收集主进程和渲染进程的崩溃报告，并附带 App 版本、Electron 版本、平台和进程类型等信息。是否上传可由应用设置控制。

可借鉴点：

- 崩溃采集必须尽早在主进程启动；
- 崩溃数据与用户主动填写的说明通过反馈 ID 关联；
- 默认上传策略需要和产品隐私设置一致。

参考：<https://www.electronjs.org/docs/latest/api/crash-reporter>

## 5. 总体产品形态

采用“三层入口、同一条提交流程”。

### 5.1 全局入口

建议位置：

- 用户头像或主菜单中的“反馈与建议”；
- Windows/macOS 应用菜单中的“帮助 > 反馈与建议”；
- 快捷键 `Ctrl/Cmd + Shift + F`。

适用场景：

- 产品意见；
- 使用建议；
- 新需求；
- 无法对应到具体错误的问题。

### 5.2 上下文入口

建议在下列位置提供“反馈这个问题”或轻量的赞踩入口：

- AI 回复旁的赞/踩按钮；
- 工具执行失败卡片；
- Runtime、登录、模型连接错误提示；
- 文件解析或预览失败提示；
- 长任务失败、超时或疑似卡住提示；
- 设置页中的“没有我需要的选项”。

上下文入口自动携带当前模块、错误、任务以及关联 ID，用户不需要重新描述自己刚才做了什么。

### 5.3 崩溃恢复入口

App 检测到上一次异常退出后，在重新启动时展示：

> OpenDrSai 上次意外退出。发送崩溃报告可以帮助我们修复问题。

操作：

- `一键发送`；
- `查看报告内容`；
- `暂不发送`。

该场景不应强制用户填写描述。用户选择“一键发送”即可完成一份包含崩溃转储和安全诊断摘要的反馈。

## 6. 核心交互

### 6.1 默认轻量面板

```text
遇到了什么？

[ 出错了 ] [ 不好用 ] [ 有建议 ] [ 想要新功能 ]

简单说一句（可选）
┌──────────────────────────────┐
│ 比如：运行到一半一直卡住       │
└──────────────────────────────┘

✓ 附带脱敏诊断信息
□ 附带当前窗口截图
□ 希望我们联系我

[查看将发送的信息]                       [发送反馈]
```

### 6.2 输入负担规则

- “出错了”：描述默认可选，因为系统应能够提供错误现场。
- “不好用”：描述可选，但可以提示用户说出预期行为。
- “有建议”和“想要新功能”：至少需要一句自然语言描述。
- 不要求填写系统版本、App 版本、模型名称、错误码或日志。
- 已登录用户不重复填写联系方式；匿名用户只有在选择“希望联系我们”时才填写联系方式。

### 6.3 提交结果

成功后显示：

> 已收到，谢谢。反馈编号：`FB-20260814-XXXX`

可以提供：

- `复制反馈编号`；
- `查看反馈内容`；
- `继续使用 App`。

不应使用阻塞式成功页面影响用户继续工作。

### 6.4 提交失败

- 网络不可用时将反馈加密暂存到本地队列；
- 网络恢复后自动重试，但在首次提交时明确告知用户；
- 用户可以在设置中删除未发送反馈；
- 重试需使用幂等键，避免生成重复反馈。

## 7. 自动采集的数据

### 7.1 默认附带的安全诊断摘要

- 反馈 ID、创建时间和入口来源；
- App、Runtime、Electron 和操作系统版本；
- 安装渠道、更新状态和语言；
- 当前功能模块和页面；
- 错误码、异常类型、脱敏调用栈；
- Gateway、模型连接及必要的网络状态；
- `workspaceId`、`threadId`、`runId`、`traceId` 等关联标识；
- 最近 50～100 条脱敏操作 breadcrumb；
- 最近失败工具的名称、状态、耗时和结果类型；
- 诊断包版本、大小、完整性 hash 和脱敏统计。

默认数据应设定时间窗口和大小上限，避免一次反馈包含无界日志。

### 7.2 需要用户单独授权的数据

- 当前窗口截图；
- 当前 AI 回复和有限的相邻上下文；
- 更详细的应用、Runtime 或网络日志；
- 文件类型、大小、解析状态等文件元数据；
- 已脱敏的工作区路径；
- 用户主动启动的问题复现记录。

### 7.3 禁止直接上传的数据

- API Key、Token、Cookie 和登录凭据；
- SSH 密钥及完整 SSH 配置；
- 完整本地路径、系统用户名和用户目录；
- 用户文件原文和工作区源码；
- 完整聊天历史；
- 终端环境变量和命令历史；
- 模型原始请求正文；
- 未经过脱敏器处理的日志。

## 8. 隐私与安全设计

### 8.1 上传前预览

“查看将发送的信息”至少展示：

- 数据分类；
- 每类数据的用途；
- 是否包含截图或对话内容；
- 诊断包大小；
- 脱敏命中数量；
- 数据保留时间和删除方式。

技术 JSON 可以作为二级详情展示，但不应成为普通用户唯一能理解的预览。

### 8.2 统一脱敏

所有反馈入口必须经过同一个脱敏管道，至少识别：

- 常见密钥和 Bearer Token；
- URL 查询参数中的凭据；
- 邮箱、手机号和 IP 地址；
- Windows/macOS 用户目录与绝对路径；
- Git remote 中的认证信息；
- 环境变量中的敏感字段；
- 对话或日志中的已知凭据格式。

### 8.3 数据策略

- 传输使用 TLS；
- 本地暂存和服务端附件均加密；
- 反馈正文和诊断附件分开存储并分别授权；
- 设置最短必要保留期；
- 记录查看、下载和删除诊断附件的审计日志；
- 企业策略可锁定远程传输、截图和详细诊断能力。

## 9. 服务端反馈闭环

### 9.1 反馈记录模型

建议反馈主记录至少包含：

```text
feedback_id
created_at
category: bug | usability | suggestion | feature_request
source: global | error | message | tool | crash | recovery
summary
user_description
contact_allowed
app_version / platform / locale
workspace_id / thread_id / run_id / trace_id
error_fingerprint
diagnostic_package_id
status
duplicate_of
fixed_in_version
```

### 9.2 自动处理

反馈进入后台后自动完成：

1. 校验包格式、完整性和大小；
2. 执行服务端二次脱敏扫描；
3. 基于错误类型、调用栈和模块生成错误指纹；
4. 合并同类问题并统计受影响用户数；
5. 分类为 Bug、体验问题、建议或需求；
6. 根据模块和严重度路由到负责人；
7. 关联已有 issue 或生成待确认事项。

### 9.3 状态模型

- `received`：已收到；
- `triaged`：已分类；
- `investigating`：调查中；
- `needs_info`：需要补充信息；
- `planned`：已进入计划；
- `fixed`：已修复；
- `closed`：已关闭或不处理。

用户只有在选择允许联系时才接收状态更新。内部状态中不宜承诺具体发布时间。

### 9.4 优先级

错误类反馈建议综合评估：

```text
优先级 = 受影响用户数 × 严重程度 × 复现频率 × 核心流程阻塞系数
```

需求类反馈不能只按提交数量排序，还需要结合用户目标、产品方向、影响范围和实现成本。

## 10. 与现有 Desktop 能力的关系

现有能力审计已指出：

- Crash Recovery 有部分基础能力，但没有正式的 `crashReporter`；
- 没有 Crash Report 数据通道；
- 没有用户主动问题反馈入口；
- 没有正式的桌面截图输入入口。

相关记录位于：

- `apps/desktop/docs/desktop-capability-governance/01_Desktop_Agent_Capability_Catalog.md`

同时，现有 Desktop 已具备可复用的诊断基础：

- `ProductionDiagnosticMode` 支持 `off / basic / detailed / interactive`；
- 支持保留天数、磁盘上限和远程传输策略；
- 支持脱敏、加密诊断包、完整性 SHA-256 和包预览；
- 已有诊断事件、快照、导出和 issue 更新接口；
- 已有 `workspaceId / threadId / traceId` 等关联信息；
- 登录与 Codex Runtime 页面已有“复制脱敏诊断”能力；
- Renderer API 已包含 `capturePage()` 能力定义。

因此应在现有 diagnostics 之上增加反馈编排层，而不是重新建设一套日志系统：

```text
全局/上下文/崩溃入口
          ↓
   Feedback Composer
          ↓
上下文快照 + Diagnostics
          ↓
  脱敏、裁剪、用户授权
          ↓
   Feedback Transport
          ↓
服务端去重、分派与跟进
```

## 11. 建议技术边界

### 11.1 Shared API

在 `apps/desktop/shared/api` 定义跨平台协议：

- `FeedbackCategory`；
- `FeedbackSource`；
- `FeedbackContext`；
- `FeedbackAttachmentManifest`；
- `FeedbackPackagePreview`；
- `FeedbackSubmitRequest/Result`；
- `PendingFeedbackItem`。

### 11.2 Main Process

主进程负责：

- 从各诊断源生成受控快照；
- 读取应用和平台版本信息；
- 生成截图或崩溃附件；
- 脱敏、限流、加密和完整性校验；
- 维护离线发送队列；
- 调用反馈上传接口；
- 提供 crash recovery 状态。

Renderer 不应直接读取日志文件或上传附件。

### 11.3 Renderer

Renderer 负责：

- 展示轻量反馈面板；
- 将当前页面、模块和对象 ID 作为上下文传给主进程；
- 展示诊断包的用户可读预览；
- 收集用户明确授权；
- 展示提交结果和反馈编号。

### 11.4 Crash Reporter

- 在 Electron 主进程早期启动；
- 初期可配置为只在本地收集，待用户授权后上传；
- 通过匿名安装 ID、App 版本和 crash ID 与反馈主记录关联；
- 设置速率限制和保留期限；
- crash minidump 与常规诊断包分开治理。

## 12. P1（一阶段）实施范围

P1 需要一次性交付从用户发起反馈、App 自动还原现场、用户确认授权、服务端接收分诊到崩溃恢复反馈的完整闭环。

### 12.1 必须交付

- 全局“反馈与建议”入口；
- 主要错误卡片上的“一键报告”；
- 四种反馈类型；
- 默认附带脱敏诊断摘要；
- 上传前预览；
- 服务端接收、反馈编号和内部列表；
- 离线暂存和幂等重试；
- 反馈入口曝光、打开、提交和失败埋点。
- 接入 Electron `crashReporter`；
- 启动后的崩溃恢复反馈；
- 当前窗口截图及敏感区域涂抹；
- 最近操作 breadcrumb 环形缓冲区；
- 错误指纹和自动聚类；
- 可选的详细诊断附件；
- 修复版本关联。

### 12.2 本阶段不包含

- 完整的客服工单系统；
- “开始录制问题—复现—停止并提交”的问题录制能力；
- 远程调试和自动根因分析；
- 用户可见的完整反馈状态中心；
- 修复发布后的自动通知；
- 跨版本趋势、版本回归和高频需求的高级分析。

这些能力可在 P1 数据质量和反馈量达到稳定水平后另行立项，不属于本方案的交付承诺。

### 12.3 P1 完成定义

P1 只有同时满足以下条件才算完成：

1. 用户可从全局入口、主要错误现场和崩溃恢复提示发起反馈；
2. 普通错误无需填写技术信息即可提交一份可定位的诊断报告；
3. 截图、详细日志和对话上下文均经过单独授权；
4. 网络中断不会丢失反馈，也不会因重试生成重复记录；
5. 后台能够按错误指纹聚类、分派并关联修复版本；
6. 第 13 节的用户体验、反馈质量和安全指标通过验收。

## 13. 验收指标

### 13.1 用户体验指标

- 反馈提交完成率 ≥ 70%；
- 错误类反馈中位完成时间 ≤ 15 秒；
- 上下文错误反馈平均用户输入字段数 ≤ 1；
- 反馈面板本身引起的任务中断和退出率可控。

### 13.2 反馈质量指标

- 错误反馈可定位率 ≥ 80%；
- 需要再次询问版本、日志或错误现场的比例持续下降；
- 有效反馈中能关联模块和版本的比例 ≥ 95%；
- 重复错误可以稳定归并，且不丢失受影响用户数。

### 13.3 安全指标

- 默认诊断包不包含凭据、完整路径、文件正文和聊天全文；
- 所有上传均通过客户端和服务端两次敏感信息扫描；
- 用户可以预览、取消和删除未发送反馈；
- 企业策略能够禁止远程传输或锁定诊断等级。

## 14. 待确认的产品决策

进入开发前需要确定：

1. 反馈后端自建，还是接入现有 issue/customer-support 系统；
2. 匿名用户是否允许提交，以及如何限制滥用；
3. 默认是否允许上传 basic 级诊断摘要；
4. 崩溃报告采用每次询问、首次授权长期生效，还是完全手动；
5. 反馈保留时间及用户删除机制；
6. 谁负责每日分诊、状态维护和修复版本回填；
7. P1 首批接入哪些错误卡片和核心流程。

## 15. 结论

OpenDrSai Desktop 的用户反馈功能应优先建设“自动还原现场”的能力，而不是追求更完整的用户表单。

P1 需要把两个核心场景做透：

1. 用户遇到明确错误时，点一次即可把安全、完整的现场信息送达；
2. 用户有意见或需求时，只需选择类型并说一句话。

## 16. 已确认的接收架构

P1 采用三层职责分离：

- Web 服务是唯一事实来源，负责接收、幂等、存储、状态流转、附件加密、权限和审计；
- Dr. Zhengde Agent 只读取经过脱敏和字段裁剪的事实投影，负责摘要、分类、严重度、聚类与建议负责人，不直接修改产品数据；
- 邮箱只接收不含正文、联系方式和诊断附件的内部通知，并作为人工联系用户的渠道，不作为反馈数据库。

Desktop 默认通过本机 Gateway 投递；部署独立接收服务时，通过 `OPENDRSAI_FEEDBACK_SERVICE_URL` 指定地址，并使用 `OPENDRSAI_FEEDBACK_INTAKE_TOKEN` 鉴权。服务端必须显式设置 `OPENDRSAI_FEEDBACK_ALLOW_REMOTE=1` 才接受非本机请求。企业可通过 `OPENDRSAI_FEEDBACK_DISABLED`、`OPENDRSAI_FEEDBACK_ALLOW_SCREENSHOT` 和 `OPENDRSAI_FEEDBACK_ALLOW_DIAGNOSTICS` 禁止远程反馈或锁定附件能力。

用户联系方式单独加密保存。操作员只有在用户授权后才能显式查看，每次查看均记录操作人、时间和结果；Agent 与内部通知邮件均不能读取联系方式。

最终的产品判断标准是：用户花费更少时间，研发获得更多可行动信息，并且整个过程对隐私数据可见、可控、可审计。
