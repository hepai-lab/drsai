# OpenDrSai Windows App 面向普通用户的产品测评与验收方案

## 1. 文档目标

本文基于《OpenDrSai 面向普通用户的产品功能设计》，定义 Windows App 要实现面向普通用户的产品体验时：

- 应测试哪些功能类别；
- 每类包含哪些用户可感知的功能点；
- 每个功能点如何测试；
- 满足什么条件才能判定“已经实现”；
- 产品在什么条件下可以面向真实用户发布。

本文测评的不是“代码中是否存在按钮、接口或智能体能力”，而是：

> 一个不了解模型、智能体、工具和工作流的普通用户，能否独立把事情交给 OpenDrSai，并获得看得懂、可使用、可信赖的结果。

## 2. “功能已经实现”的统一定义

功能完成度只采用自动化验收结果。一个功能点只有同时满足以下五层自动化标准，才标记为“已实现”。人工访谈、观察和主观评分只用于发现体验问题，不计入完成度，也不作为发布阻断条件。

| 层级 | 自动化判断 | 通过条件 |
| --- | --- | --- |
| 入口存在 | 用户入口是否在约定页面和状态下可访问？ | 打包版 UI E2E 能通过可访问名称或稳定测试标识找到入口，并用键盘触发 |
| 信息可解释 | 页面是否提供完成操作所需的标签、说明、状态和下一步？ | DOM、可访问树、文案规则和禁用技术术语扫描全部通过；不以“让用户觉得懂了”作为自动断言 |
| 闭环可完成 | 是否能从输入自动执行到成果？ | 打包版 E2E 不调用开发者接口、不修改数据库、不人工补步骤，完整走通 |
| 结果可校验 | 输出是否符合结构、事实、数字、来源、安全和文件格式要求？ | 黄金数据规则校验全部通过；生成式结果通过结构化语义评分阈值；关键数字、安全边界采用确定性断言 |
| 稳定可重复 | 是否稳定，而非只成功演示一次？ | 确定性功能连续 20 次全通过；AI 功能在固定黄金集上成功率不低于 85%；安全、隐私、数据损坏项必须 100% 通过 |

以下情况不能算“已实现”：

- 只有后端接口，没有普通用户入口；
- 只有按钮或静态页面，没有真实执行；
- 需要用户配置模型、工具、提示词或技术参数才能完成；
- 只能在开发环境、Mock 数据或固定演示脚本中成功；
- 结果生成了，但用户无法查看、修改、保存或确认依据；
- 成功一次，但重复运行经常失败；
- 遇到错误只能看日志，界面没有恢复办法。

### 2.1 自动化验收类型

本文使用以下标签描述自动验收方式：

| 标签 | 含义 | 适用内容 |
| --- | --- | --- |
| `UI-E2E` | 在真实打包版 Windows App 中模拟鼠标、键盘、拖放、重启和窗口操作 | 入口、流程、状态、成果、恢复 |
| `CONTRACT` | 对 IPC、状态机、持久化、权限和文件格式做确定性断言 | 数据结构、边界和一致性 |
| `GOLDEN` | 使用固定材料和预埋事实核对结果 | 数字、异常点、引用、冲突、材料关系 |
| `SEMANTIC` | 将生成结果转为结构化字段，通过规则和独立评测模型评分 | 需求理解、计划完整性、摘要覆盖度；不得单独用于安全关键判断 |
| `SECURITY` | 对越权、泄漏、覆盖、删除和分享边界做攻击性回归 | 一票否决项，要求 100% 通过 |
| `VISUAL/A11Y` | 截图差异、布局边界、可访问树和 axe 规则检查 | 缩放、遮挡、键盘、语义标签 |

每个自动用例必须保存输入材料版本、随机种子（如适用）、模型与服务版本、事件轨迹、截图、成果文件及断言结果。只通过 Mock renderer 的测试不能作为最终完成证据；至少需要一条打包版 E2E 证据。

## 3. 测试对象与环境

### 3.1 目标测试用户

至少覆盖三类用户：

1. **完全新手**：没有使用过智能体产品，不了解模型、MCP、Skills 和工作流。
2. **普通科研用户**：会使用 Office、浏览器和常见科研软件，但不会编程。
3. **科研工程用户**：能理解数据、代码和计算过程，但不参与 OpenDrSai 开发。

这些人群用于可选的体验观察和产品研究。观察结果用于发现问题和调整设计，但不计入功能完成分数，也不替代自动化验收。

### 3.2 Windows 环境矩阵

至少覆盖：

- Windows 11 x64 最新稳定版；
- Windows 10 x64 仍支持的稳定版；
- 1920×1080、150% 缩放；
- 1366×768、100% 缩放；
- 普通用户权限账户；
- 中文用户名及包含空格、中文的工作目录；
- 正常网络、慢速网络、短时断网；
- 干净安装、覆盖升级、异常退出后恢复。

### 3.3 测试证据

每次正式验收至少保留：

- 测试版本、Windows 版本和运行环境；
- 用户输入、使用材料和期望结果；
- 操作录像或关键步骤截图；
- 任务事件记录和最终成果；
- 用户是否独立完成、耗时和求助次数；
- 失败原因及是否可恢复；
- 自动化测试报告。

## 4. 标准测试材料与黄金任务

为了让版本之间可比较，应维护一套不随模型输出变化而失去判定依据的固定材料。

### 4.1 标准材料包

| 编号 | 材料 | 预埋验证点 |
| --- | --- | --- |
| D1 | 一篇 8～15 页中文或英文论文 PDF | 标题、作者、研究问题、方法、三条明确结论和两个限制条件 |
| D2 | 一份 CSV 与一份 Excel 实验数据 | 已知均值、趋势、缺失值、重复行和两个异常点 |
| D3 | 三篇围绕同一主题的论文 | 两项一致结论、一项来源冲突、一项仍缺乏证据的结论 |
| D4 | Word 旧报告、最新数据和一张结果图 | 报告中一个过期数字；图表中一处与数据不一致 |
| D5 | 图片、扫描 PDF、带中文文件名文件 | OCR、中文路径和多模态识别 |
| D6 | 大文件、损坏文件、密码保护 PDF、未知格式文件 | 失败提示和恢复路径 |
| D7 | 含手机号、邮箱、API Key 样例和个人信息的材料 | 敏感信息识别、分享和日志脱敏 |
| D8 | 可安全修改的测试工作区 | 版本、撤销、冲突、工作区外访问和异常退出恢复 |
| D9 | CERN Indico 演示型 PDF：`WLCG-20260715-WLCG-talk-IHEP-visit.pdf` | 48 页、由 LibreOffice Impress 导出；包含章节页、网络结构图、关键数字、Data Challenge 路线和总结页。来源：[CERN Indico PDF](https://indico.cern.ch/event/1678348/contributions/7063019/attachments/3313017/5929652/WLCG-20260715-WLCG-talk-IHEP-visit.pdf) |

D9 自动测试必须固定资产版本，避免远程文件变化或网络故障造成误判：

- 文件长度：`7,664,262` bytes；
- SHA-256：`F6581E1A255B354667188B41B874B996A300F88BB48912721BC1C854183E913E`；
- 页数：48；
- PDF Creator：`Impress`；
- CI 优先使用校验过的缓存副本；来源 URL 只用于首次获取或显式刷新夹具；
- 下载结果不匹配哈希时应标记“测试资产变化”，不得继续使用旧黄金答案判定产品失败。

### 4.2 黄金任务集

| 编号 | 用户任务 | 主要覆盖能力 |
| --- | --- | --- |
| G1 | “帮我看懂这篇论文，我不是这个方向的专家。” | 新手引导、材料理解、结果表达、依据 |
| G2 | “帮我看看这份数据有没有问题。” | 模糊需求澄清、计划、数据分析、图表和异常解释 |
| G3 | “综合这些材料，告诉我目前共识、争议和下一步值得研究的问题。” | 多材料关联、冲突发现、引用和不确定性 |
| G4 | “把最新数据更新进旧报告，生成给导师看的版本。” | 材料关系、成果编辑、数字核对和版本保存 |
| G5 | “认真完成这个任务，完成后通知我。” | 长任务、关闭应用、恢复、通知和阶段成果 |
| G6 | “尝试另一种分析方法，但保留现在的结果。” | 分叉、比较、版本和撤销 |
| G7 | “以后每周帮我检查同类数据。” | 保存任务、复用、定时执行和结果摘要 |
| G8 | “把结果分享给同事，但不要分享原始数据和个人信息。” | 分享范围、权限、脱敏和撤销分享 |
| G9 | “分析这份 PPT 导出的 PDF，生成一份给非专业管理者看的 10 页中文 PPT，并附逐页讲稿。” | 演示型 PDF 识别、故事线提取、页码溯源、受众改写、PPTX 生成与格式校验 |

## 5. 待测功能类别与逐项验收标准

## A. 首次使用与任务入口

| ID | 功能点 | 自动化测试 | 自动验收标准 |
| --- | --- | --- | --- |
| A1 | 首次打开即可看到产品用途和主入口 | `UI-E2E + VISUAL/A11Y`：以空用户数据首次启动，检查首屏、焦点和可访问树 | 3 秒内出现可交互首屏；主任务输入框位于首屏且自动获得焦点；存在产品用途说明和可访问名称；首屏不得要求配置模型、Agent、MCP、API Key 或工作流 |
| A2 | 自然语言直接交代任务 | `UI-E2E`：分别输入 G1、G2，不触碰高级设置 | 两个请求均直接创建任务并进入运行状态；从页面可交互到请求提交不超过 120 秒的自动流程预算；网络请求中包含任务而不依赖预先人工配置技术参数 |
| A3 | 场景化快捷入口 | `UI-E2E`：通过可访问名称定位“读论文、分析数据、写报告、制作图表、长期跟踪”，逐一点击 | 所有计划发布入口均存在、可键盘触发；点击后填入可编辑自然语言模板；模板可直接提交或附加材料，不跳转到模型/工具配置页 |
| A4 | 示例任务可直接使用 | `UI-E2E`：点击示例、替换主题、导入材料并运行 | 输入框内容可编辑；提交后创建真实 run；完成后产生至少一个成果对象；测试禁止调用演示专用后门或静态结果 |
| A5 | 无可用服务时的引导 | `UI-E2E + CONTRACT`：注入未登录、服务不可用、运行时缺失、账号无权限四种故障 | 每种故障在超时阈值内进入明确错误状态；页面包含原因、重试及至少一个可执行恢复入口；不得无限 loading；界面不直接暴露堆栈、裸错误码或密钥 |

## B. 模糊需求理解与任务澄清

| ID | 功能点 | 自动化测试 | 自动验收标准 |
| --- | --- | --- | --- |
| B1 | 理解模糊需求 | `GOLDEN + SEMANTIC`：运行 20 个模糊请求，每个样例定义必需意图字段和禁止动作 | 至少 17 个样例形成符合 schema 的可执行目标或提出必要澄清；所有样例均不得执行其禁止动作；安全相关误判为 0 |
| B2 | 用少量问题补齐关键信息 | `GOLDEN + SEMANTIC`：G2 缺分析目的、G4 缺受众，记录澄清事件 | 必需信息缺失时产生 1～3 轮澄清；问题包含缺失字段并提供结构化选项；已有信息不得重复询问；完成后目标 schema 无必需字段缺失 |
| B3 | 开始前复述目标 | `UI-E2E + CONTRACT`：完成澄清，读取目标确认卡及操作 | 确认卡包含目标、材料、输出和限制字段；存在“确认、修改、补充”三个可执行动作；确认前不得执行有副作用步骤 |
| B4 | 用户可以纠正理解 | `UI-E2E + CONTRACT`：提交纠正消息并检查任务目标版本与后续事件 | 生成新目标版本；被否定字段不再出现在活动目标和后续计划中；旧理解保留在历史但不得继续驱动执行 |
| B5 | 自动补全输出要求 | `GOLDEN + CONTRACT`：运行缺少受众、篇幅、语言、引用和格式的请求 | 系统通过澄清或带来源标识的默认值补齐字段；最终成果元数据和内容遵守这些字段；默认值必须标记为系统默认，不得伪装成用户确认 |

## C. 材料导入、识别与使用

| ID | 功能点 | 自动化测试 | 自动验收标准 |
| --- | --- | --- | --- |
| C1 | 拖放与选择文件 | 分别拖入 D1～D7 中的 PDF、Word、Excel、CSV、图片和多个文件 | 支持的文件能被导入并显示名称、类型、大小和状态；失败文件不影响其他文件；用户不需要预先转换格式 |
| C2 | 文件夹和多文件导入 | 导入包含 30 个混合文件和子目录的材料文件夹 | App 不假死；显示扫描进度、已导入/跳过/失败数量；重复文件和不支持格式有可理解说明 |
| C3 | 自动识别材料角色 | 导入 D4，询问系统拥有了哪些材料 | 能区分旧报告、最新数据、结果图片和参考材料，并给出合理用途建议；关键材料识别准确率不低于 90% |
| C4 | 主动建议可以做什么 | 只上传 D1、D2 或 D4，不输入任务 | 在合理位置给出 2～4 个与材料相关的建议，例如“提取论文要点”“检查数据异常”；建议点击后可直接形成任务 |
| C5 | 多材料关联与冲突发现 | 使用 D3 和 D4，要求比较材料 | 必须找出预埋的一致点、冲突点或过期数字；每个判断可回到具体文件和位置；不得混淆文件来源 |
| C6 | 自然语言查询材料 | 连续询问标题、某个数字、某篇材料中的方法和跨文件差异 | 黄金问题正确率不低于 90%；回答标明来源；找不到时明确说明，不编造位置 |
| C7 | 异常文件处理 | 导入 D6 中的大文件、损坏文件和密码保护文件 | 60 秒内给出明确状态；说明无法处理的原因和用户可采取的措施；不导致任务永久卡住或 App 崩溃 |
| C8 | 中文路径和隐私保护 | 从含中文和空格的路径导入 D5、D7，并查看日志和界面 | 正常读取和展示；敏感值不出现在日志、通知和无关界面；材料未经用户操作不会自动公开分享 |
| C9 | 识别 PPT 导出的演示型 PDF | `GOLDEN + CONTRACT`：导入 D9，解析元数据、页面尺寸、文本布局和页面结构 | 识别结果为“演示报告/幻灯片 PDF”而非论文；页数为 48；识别封面、议程、章节、内容、总结和问答等页面角色；关键页面角色黄金准确率不低于 90% |

## D. 自动规划与连续完成任务

| ID | 功能点 | 自动化测试 | 自动验收标准 |
| --- | --- | --- | --- |
| D1 | 自动拆成用户任务步骤 | `GOLDEN + SEMANTIC`：对 G2、G3、G4 生成结构化计划并进行术语扫描 | 计划覆盖输入、处理、检查和输出必需阶段；语义覆盖率不低于 90%；步骤标题不包含内部 Agent、工具函数、MCP server、JSON 参数等禁用术语 |
| D2 | 用户编辑计划 | 删除一步、调整顺序、补充“必须有引用”，然后执行 | 实际执行遵守修改后的计划；被删除步骤不会暗中执行；新增要求进入最终结果 |
| D3 | 快速/标准/深入等深度选择 | 同一任务分别选择不同深度执行 | 界面说明预计时间和输出差异；三种结果在材料覆盖、检查深度或交付物上有可验证差异，而非只改变文字长度 |
| D4 | 自动连续完成中间步骤 | 执行 G3，不逐步告诉系统搜索、阅读、整理和写报告 | 系统在一次任务中完成必要中间步骤，只有关键决策才询问用户；最终形成完整成果 |
| D5 | 计划变化可见 | 执行中制造某个数据源不可用，观察计划调整 | 系统说明哪一步失败、为何调整及对结果的影响；不会静默跳过关键步骤后仍宣称完整完成 |
| D6 | 完成标准明确 | 用户说“认真检查后再给我”，执行 G4 | 任务完成卡片说明做了什么、哪些检查通过、哪些未完成和剩余风险；不能只显示“任务完成” |

## E. 执行进度、介入与长任务

| ID | 功能点 | 自动化测试 | 自动验收标准 |
| --- | --- | --- | --- |
| E1 | 用业务语言显示当前进度 | `UI-E2E + CONTRACT`：执行 G3、G5，在每个状态事件采集可见状态文案 | 每个后台阶段在 2 秒内映射为可见的用户阶段；状态与 run 状态机一致；文案通过业务术语白名单/技术噪声黑名单检查，不展示裸工具调用作为唯一进度 |
| E2 | 统一任务状态 | 分别触发等待、运行、需要决定、成功和失败 | 每种状态有清晰且一致的视觉表现；列表状态与任务详情一致；不存在任务已失败但仍显示运行中的情况 |
| E3 | 阶段性结果 | 运行超过 10 分钟的任务 | 在最终完成前提供至少一个可查看的阶段成果；阶段成果明确标记为临时结果，后续更新不会无提示覆盖 |

## 7. 自动化验收实施要求

### 7.1 所有完成目标必须自动化

下列内容必须进入持续集成或 Windows 定时验收，不能以人工勾选代替：

- 安装、启动、更新和回滚；
- 首屏入口、导航、键盘操作和可访问树；
- 文件导入、中文路径、异常格式和材料关系；
- 模糊需求、澄清、目标确认和计划生成；
- 会话、任务、成果、记忆和版本持久化；
- 暂停、取消、断线、崩溃和关闭窗口后的恢复；
- 工作区边界及所有高风险未授权操作；
- 敏感信息在日志、通知、导出和分享中的脱敏；
- 定时任务单次触发、补跑、暂停和删除；
- 分享权限、越权访问和撤销；
- 黄金数据中的数字、异常点、材料冲突、引用和图表；
- 全部核心流程的 Windows 打包版 E2E。

### 7.2 原人工项的自动化替代

| 原人工问题 | 自动化替代方法 | 自动化能证明什么 |
| --- | --- | --- |
| 首次打开是否知道怎么用 | 首屏视觉快照、主输入框自动聚焦、可访问名称、导航步数和禁止技术配置断言 | 入口存在、位置稳定、无需技术配置即可开始 |
| 澄清是否自然 | 固定模糊语料、必需字段 schema、轮次上限、重复问题检测和语义评分 | 澄清覆盖必要信息且不过度询问 |
| 计划是否看得懂 | 阶段字段完整性、句长、术语黑名单、步骤数量和语义覆盖评分 | 计划具备用户任务结构且没有明显技术噪声 |
| 进度是否看得懂 | run 状态到业务状态的一一映射、文案规则和可访问状态断言 | 用户界面始终有与后台一致的业务状态 |
| 审批是否能理解影响 | 审批 schema 强制动作、对象、范围、影响、风险和选项字段 | 决策所需信息在界面中完整存在 |
| 成果是否可直接使用 | 文件可解析、章节完整、黄金事实覆盖、无占位符、格式与跨输出数字一致性 | 成果具备可交付的客观结构和事实质量 |
| 风险标签是否易懂 | 标签定义、建议动作、非颜色表达和可访问名称断言 | 每个风险状态都有完整解释与下一步 |
| 离开后能否接上任务 | 重启恢复 E2E、离开摘要结构和 deep link 测试 | 状态不丢失且界面提供继续所需信息 |

这些替代指标是完成度判据。它们不宣称能够证明用户的主观感受，只证明产品提供了支持该体验的可验证条件。

### 7.3 AI 能力的自动评测方式

AI 功能不能以固定字符串断言作为唯一标准。应采用：

1. 黄金事实和数字的程序化核对；
2. 来源与引用的可访问性核对；
3. 使用冻结版本的独立评测模型按明确量表输出结构化 JSON 分数；
4. 对评测模型结果做 schema、范围和证据引用校验；
5. 在同一版本、同一设置下重复运行并计算成功率；
6. 记录模型与服务版本，以区分产品回归和模型波动；
7. 关键数字、权限、安全和隐私不得依赖评测模型判断，必须使用确定性断言。

### 7.4 自动测试失败处理

- 任一一票否决用例失败，整个版本自动判定不通过；
- AI 输出未达到阈值时保存原始输入、输出、轨迹和评测理由；
- 同一用例最多按预先定义的重试次数执行，不允许失败后人工挑选一次成功结果；
- 不稳定用例必须标记为失败或隔离，不得由人工改成通过；
- 模型升级后必须重新运行完整黄金集，不沿用旧版本结果。

## 8. 评分方法

每个功能点按 0～3 分记录：

| 分值 | 状态 | 定义 |
| --- | --- | --- |
| 0 | 未实现 | 无入口、无真实能力或无法完成 |
| 1 | 原型 | 只有组件/契约测试或 Mock 演示，打包版闭环尚未通过 |
| 2 | 可用 | 打包版自动 E2E 可完成，但黄金集覆盖、重复稳定性或异常恢复尚未达到阈值 |
| 3 | 已实现 | 本文规定的入口、闭环、质量、安全和重复性自动验收全部通过，并保存完整机器可读证据 |

类别得分计算：

`类别得分 = 实际得分之和 ÷ 该类别满分 × 100%`

禁止用平均分掩盖安全和数据正确性问题。下列项目为一票否决项：

- 未授权文件、网络、计算或分享操作；
- API Key、令牌或敏感数据明文泄漏；
- 用户原始文件被错误删除或覆盖且无法恢复；
- 关键数字与黄金数据不一致，却被系统标记为可信；
- 虚构引用或引用无法支持结论；
- 应用崩溃导致会话或已完成成果永久丢失。

## 10. 与现有 Windows App 技术验证的关系

现有 `apps/desktop/windows/scripts/verify-*.mjs`、打包烟雾测试和 E2E 测试可以作为底层证据，但不能单独证明用户功能已实现。

每个产品功能应建立三层自动化证据：

1. **单元/契约层**：数据、状态、安全策略和持久化正确；
2. **打包版 E2E 层**：真实 Windows App 中完整流程可运行；
3. **产品闭环层**：从用户可见入口出发，在打包版中不使用开发后门完成任务，并自动校验结果。

产品功能状态表应同时链接这三类证据。只有三层自动证据都满足本文标准，才能从“技术能力存在”升级为“用户功能已实现”。人工观察结果可以链接为补充信息，但不改变功能分数。

## 12. 单独记录的人工体验观察项（不计完成度）

以下问题涉及人的理解、情绪、审美、信任和价值感，无法被自动化测试可靠证明。可以定期开展用户研究，但结果只进入体验改进清单，不作为功能完成目标、发布分数或一票否决项。

| 观察项 | 建议记录方法 | 不自动化的原因 |
| --- | --- | --- |
| 用户第一眼是否知道产品能做什么 | 首次使用录像、首次点击位置、访谈原话 | DOM 中有说明不等于人真正理解 |
| 澄清对话是否自然、是否令人厌烦 | 任务后访谈、主观 1～5 分和典型原话 | “自然”和“厌烦”属于主观感受 |
| 计划和进度是否让用户安心 | 观察用户是否反复询问、访谈信心变化 | 自动化只能证明信息存在，不能证明安心 |
| 审批是否真的让用户理解风险 | 让用户用自己的话复述后记录误解 | 字段完整不等于用户形成正确心智模型 |
| 成果是否愿意直接交给导师或同事 | 询问是否愿意使用、还会修改什么 | 可交付意愿取决于场景、责任和个人标准 |
| 风险标签是否增强或削弱信任 | 访谈标签前后的信任变化 | 信任不是可由界面元素确定性推导的属性 |
| 整体是否感觉省事 | 与原工作方式比较耗时和主观负担 | 自动脚本只能测系统步骤，不能测人的心理负担 |
| 是否愿意再次使用或推荐 | 复访、留存和推荐意愿 | 属于产品价值和市场反馈，不是单项功能正确性 |
| 中文表达是否自然、专业程度是否合适 | 收集不自然文案和修改建议 | 规则扫描能发现乱码和术语问题，不能完整评价语言风格 |
| 视觉是否美观、布局是否舒适 | 截图访谈和偏好记录 | 视觉回归只能检测变化，不能判断审美质量 |

人工观察记录至少包含版本、用户背景、任务、原话、录像/截图、观察者解释和改进建议。不得把人工观察结果回填为自动验收“通过”，也不得因没有开展人工研究而把已通过自动验收的功能标记为未实现。

## 13. 最终验收原则

> 完成度由可重复的自动化证据判定；人工研究只回答体验是否更好，不负责替代功能验收。
