# OpenDrSai v1.5.3 多套输出协议问题

状态：已确认  
适用版本：OpenDrSai v1.5.3  
记录日期：2026-08-02  
目标协议：OAEP v1.0（`cores/protocol/oaep`）

## 1. 问题摘要

OpenDrSai v1.5.3 已具备流式输出、结构化内容、持久事件、断线恢复和跨端会话同步能力，但这些能力分散在多套相互重叠的协议和投影模型中：

1. OpenAI-compatible Chat Completions SSE。
2. Structured Conversation v2 SSE。
3. Runtime Event。
4. Session Conversation Event。
5. Desktop `AgentRunEvent`。
6. Agent Backend 私有事件。

这些协议分别解决过不同阶段的问题，但当前缺少统一的公开领域模型和唯一的规范化事件语义。结果是同一条 Agent 输出会经过多次翻译，并可能在不同层丢失结构。

v1.5.3 的问题不是“没有结构化输出协议”，而是：

> 已经存在多套结构化输出实现，但没有收敛成一个 Backend-neutral、端到端一致的协议。

## 2. 当前协议链路

```text
Agent Backend 私有事件
        │
        ├─ OpenDrSai：message.delta / tool.start / message.complete / ...
        └─ Codex：turn/* / item/* / approval server request / ...
        │
        ▼
Backend Event Mapper
        │
        ▼
Runtime Event
        │
        ├─ Runtime Event Store（按 Run）
        ├─ Session Conversation Journal（按 Session）
        ├─ Structured Conversation v2
        ├─ OpenAI-compatible SSE
        └─ Desktop AgentRunEvent
```

同一语义可能同时拥有多个名字：

```text
message.delta
agent.message.delta
conversation.item.delta
part.delta
chunk
```

这些名字在各自局部实现中合理，但组合后形成了重复的语义层。

## 3. v1.5.3 中存在的输出协议

### 3.1 OpenAI-compatible Chat Completions SSE

入口：

```http
POST /v1/chat/completions
Accept: text/event-stream
```

传统帧：

```text
data: {"choices":[{"delta":{"content":"正在分析"}}]}

data: [DONE]
```

主要用途：

- 兼容已有 OpenAI Chat Completions 客户端。
- 为 Desktop 提供简单文本流。
- 支持已有聊天请求链路。

问题：

- `choices[].delta.content` 主要只能表达文本。
- `[DONE]` 只能表示流结束，不能完整表达 Run 终态。
- 命令、文件修改、工具、计划、推理、审批和产物缺少统一结构。
- 不应成为 OpenDrSai 内部的事实来源。

实现位置：

- `cores/python/packages/drsai/src/drsai/backend/gateway.py`
- `/v1/chat/completions`

### 3.2 Structured Conversation v2 SSE

事件名：

```text
event: drsai.event
```

事件结构：

```json
{
  "version": 2,
  "type": "part.delta",
  "turnId": "turn-id",
  "sequence": 3,
  "dedupeKey": "turn-id:3:part.delta",
  "timestamp": "2026-08-02T10:00:00Z",
  "source": "gateway",
  "partId": "turn-id:markdown",
  "delta": {
    "kind": "markdown.append",
    "text": "正在分析"
  }
}
```

已支持的结构包括：

- Turn 生命周期。
- Markdown Part。
- Reasoning Part。
- Tool Activity。
- Subtask。
- Progress。
- Artifact。
- Citation。
- Interaction。
- Notice。

问题：

- 使用 `Turn / Part / Activity` 术语，与 Runtime 的 `Session / Run / Event` 不一致。
- Part 和 Runtime Conversation Item 表达相近的内容，但不是同一个对象模型。
- 它与传统 OpenAI-compatible 帧混合在同一个 SSE 响应中。
- 消费者需要同时识别有 `event:` 的结构化帧和没有 `event:` 的传统帧。

实现位置：

- `cores/python/packages/drsai/src/drsai/backend/runtime/conversation.py`
- `StructuredConversationProjector`

### 3.3 Runtime Event

Runtime Event 是按 Run 持久化的 append-only 事件：

```json
{
  "event_id": "event-id",
  "run_id": "run-id",
  "sequence": 12,
  "type": "agent.message.delta",
  "data": {
    "content": "正在分析"
  },
  "created_at": "2026-08-02T10:00:00Z",
  "backend_event_key": "codex:turn:item:delta:12"
}
```

优点：

- append-only。
- Run 内严格递增 sequence。
- 支持事件重放和断线恢复。
- 支持 Backend Event 幂等去重。
- 支持审计和自动验收。
- 同步投影到 Session Conversation Journal。

问题：

- Event type 尚未形成统一、正式的稳定枚举。
- 同时存在 `message.delta` 和 `agent.message.delta`。
- 同时存在 `tool.start` 和 `tool.started`。
- Event 的 `data` 结构主要依靠生产者约定，缺少完整 JSON Schema。
- Runtime Event 与 Structured Conversation Event 的命名和对象结构不同。

实现位置：

- `cores/python/packages/drsai/src/drsai/backend/runtime/engine.py`
- `runtime_events` 表
- `append_event()`
- `append_backend_event()`

### 3.4 Session Conversation Event

Session Event 用于多轮会话和跨设备同步：

```http
GET /v1/sessions/{session_id}/events
GET /v1/sessions/{session_id}/events/stream
```

SSE 示例：

```text
id: 83
event: session.event
data: {"session_sequence":83,"kind":"conversation.item.delta",...}
```

事件类别包括：

```text
run.created
run.state.changed
conversation.item.created
conversation.item.delta
conversation.item.upsert
tool.state.changed
approval.created
approval.decided
artifact.created
session.updated
```

优点：

- 跨多个 Run 维护 Session 全局顺序。
- 支持 Desktop、Android 和 Relay 增量同步。
- 支持心跳、游标恢复和游标过期处理。
- 支持 Conversation Snapshot。

问题：

- Session Event 的 `kind` 与 Runtime Event 的 `type` 是两套命名体系。
- Runtime Event 到 Session Event 需要再次分类和投影。
- Conversation Item 与 Structured Conversation Part 概念重叠。
- 消费者必须理解 Run sequence 与 Session sequence 两套游标。

实现位置：

- `cores/python/packages/drsai/src/drsai/backend/runtime/journal.py`
- `cores/python/packages/drsai/src/drsai/backend/runtime/engine.py`
- `cores/python/packages/drsai/src/drsai/backend/gateway.py`

### 3.5 Desktop AgentRunEvent

Desktop 当前使用的展示事件：

```text
start
chunk
status
plan_adjustment
file_event
done
error
aborted
```

结构示例：

```ts
interface AgentRunEvent {
  requestId: string;
  sessionId: string;
  runId: string;
  type: "start" | "chunk" | "status" | "plan_adjustment" |
        "file_event" | "done" | "error" | "aborted";
  content?: string;
}
```

问题：

- 这是面向旧 UI 的有损投影。
- Tool、Reasoning、Command、Artifact 等结构可能退化成普通 `status`。
- Backend 的结构化 Item 无法完整贯穿到 UI。
- Desktop 必须维护额外的状态归并逻辑。
- Desktop Event 不应继续承担规范协议角色。

实现位置：

- `apps/desktop/shared/api/desktopApi.ts`
- `apps/desktop/shared/api/agentBackendPresentation.ts`
- `apps/desktop/shared/main/agentRuns.ts`

### 3.6 Agent Backend 私有事件

OpenDrSai Backend 现有事件包括：

```text
agent.started
agent.message.delta
agent.completed
tool.started
tool.completed
tool.failed
```

旧 Agent/TUI 事件还包括：

```text
message.delta
message.complete
thinking.delta
tool.start
tool.progress
tool.complete
status.update
progress.update
subagent.thinking
subagent.complete
```

Codex Backend 则使用 Codex App Server 私有协议：

```text
turn/started
turn/completed
item/started
item/completed
item/agentMessage/delta
item/commandExecution/outputDelta
item/*/requestApproval
```

问题：

- Backend 私有事件是必要的，但不应直接进入 Desktop。
- Adapter 当前覆盖范围不同，导致不同 Backend 的 UI 表现不一致。
- 未识别事件可能降级为 generic status 或 unknown item。

## 4. 同一个输出被多次投影

以 Assistant 文本流为例：

```text
Codex item/agentMessage/delta
    ↓
agent.message.delta
    ↓
conversation.item.delta
    ↓
part.delta + markdown.append
    ↓
OpenAI choices[].delta.content
    ↓
Desktop AgentRunEvent.chunk
```

每一层都可能进行：

- 字段重命名。
- 文本拼接。
- sequence 重新分配。
- 状态转换。
- 去重。
- 错误降级。

这增加了以下风险：

- Delta 重复或丢失。
- `[DONE]` 与真实 Run 终态不一致。
- Structured Item 在 UI 中退化为文本状态。
- 重连后不同投影层的游标不一致。
- Backend 新增事件时需要修改多个 Mapper。
- 自动验收只能验证局部协议，无法验证端到端语义一致性。

## 5. 领域模型重复

v1.5.3 同时出现以下相近概念：

| 层 | 会话 | 一次执行 | 结构化内容 | 变化记录 |
|---|---|---|---|---|
| Codex | Thread | Turn | Item | Notification |
| Runtime | Session | Run | Conversation Item | Runtime Event |
| Structured SSE | 隐含 Session | Turn | Part / Activity | `drsai.event` |
| Desktop | Session | Agent Run | chunk/status/file event | AgentRunEvent |

主要重复点：

- `Conversation Item` 与 Structured `Part`。
- Structured `Activity` 与 Tool/Command Item。
- Runtime Event 与 Desktop Event。
- Run 状态与 `[DONE]`。
- Runtime sequence、Session sequence 和 Structured sequence。

## 6. 对用户功能的影响

### 6.1 多轮会话

如果 Desktop request、Runtime Run 和 Codex Turn 的绑定不一致，用户每发送一条消息就可能创建新的 Codex Thread，而不是在同一 Session 中创建新 Run。

### 6.2 流式输出

Backend 已经产生 Delta，但如果中间投影等待完整结果，用户会看到长时间无输出，然后一次性出现最终内容。

### 6.3 结构化会话

Codex 已提供 Command、File Change、Tool Call、Reasoning 等 Item，但 Desktop 的有损投影可能只显示普通状态文本。

### 6.4 历史同步

历史读取、Runtime Event Replay、Session Snapshot 和 Codex Thread Read 使用不同对象模型，容易出现历史存在但 UI 没有正确加载的问题。

### 6.5 审批

Backend Approval、Runtime Approval、Structured Interaction 和 Desktop Approval Center 之间存在多层转换，容易出现审批已经发生但 UI 未正确关联到原始 Command 或 File Change 的情况。

### 6.6 自动验收

测试可能只证明某个局部 SSE 或 Mapper 工作正常，却没有证明：

```text
Backend Item
→ Runtime
→ Session History
→ Desktop Structured UI
```

保持了相同的 Session ID、Run ID、Item ID、顺序和终态。

## 7. OAEP 收敛方向

OAEP 将公开领域模型统一为：

```text
Session
└─ Run
   └─ Item
```

- Session：长期、多轮会话。
- Run：一次用户请求及 Agent 执行。
- Item：Run 中的结构化内容。
- Event：Session、Run 或 Item 变化的内部不可变记录，不是第四层领域对象。
- Delta：只存在于 `event.item.delta.data.delta` 内，描述该 Event 对 Item 产生的增量；它不是独立对象或独立协议消息。

统一后的链路：

```text
OpenDrSai Backend ─┐
                   ├─ Backend Adapter → OAEP Event → OAEP Item → Desktop
Codex Backend ─────┘
```

OAEP v1 Item 类型：

```text
message
reasoning
plan
command_execution
file_change
tool_call
artifact
interaction
subtask
notice
```

OAEP Event 全部使用 `event.` 前缀：

```text
event.session.*
event.run.*
event.item.*
```

完整定义见：

- `cores/protocol/oaep/README.md`
- `cores/protocol/oaep/oaep.schema.json`
- `cores/protocol/oaep/examples.json`

## 8. 收敛边界

OAEP 收敛不意味着立刻删除所有旧接口。

### 保留但降级为兼容层

- `/v1/chat/completions`。
- OpenAI-compatible `choices[].delta.content`。
- `[DONE]`。
- 旧 Desktop `AgentRunEvent`。

这些接口可以继续存在，但必须从 OAEP 投影生成，不能继续作为独立事实来源。

### 保留为内部实现

- Runtime append-only Event Store。
- Session Journal。
- Run sequence 和 Session sequence。
- Backend 私有事件。
- Codex App Server 原始协议。

这些实现继续承担持久化、恢复、跨端同步或 Backend 接入职责，但对上层统一呈现 OAEP 语义。

### 逐步替换

- Structured Conversation `Part` 统一为 OAEP Item。
- Structured `Activity` 统一为 Command、Tool Call 或 Notice Item。
- Desktop 逐步直接消费 OAEP Item/Event。
- Backend Adapter 只负责私有协议到 OAEP 的一次规范化映射。

## 9. 后续验收原则

协议收敛后的自动验收至少验证：

1. 一个 Session 的多次用户请求创建多个 Run，不创建多个 Backend Thread。
2. 每个 Run 的 Event sequence 连续且可重放。
3. 每个 Item 从 started/delta/updated 到终态的状态合法。
4. `event.item.completed.data.item` 可以校准之前所有 Delta。
5. 相同 Backend 事件重放不会产生重复 OAEP Item。
6. 历史查询直接返回 Session → Runs → Items，无需 Desktop 重放全部事件。
7. 本地 OpenDrSai Backend、本地 Codex Backend 和未来远程 Codex Backend 输出相同 OAEP 语义。
8. OpenAI-compatible SSE 与 Desktop 兼容事件均由 OAEP 投影产生。

## 10. 结论

OpenDrSai v1.5.3 的多协议问题属于协议收敛问题，而不是功能缺失问题。

正确方向不是继续增加新的平行事件模型，而是：

```text
统一数据模型：Session → Run → Item
统一变化语义：event.session.* / event.run.* / event.item.*
统一事实来源：OAEP Event + 最终 OAEP Item
旧协议定位：兼容投影层
```

这样可以保留 v1.5.3 已实现的持久化、恢复、跨端同步和兼容能力，同时消除 Backend、Runtime、Gateway 与 Desktop 之间重复且有损的协议转换。
