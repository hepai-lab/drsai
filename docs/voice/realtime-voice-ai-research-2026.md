# 2026 实时语音 AI 技术调研报告

—— 从串行语音交互到全双工 AI Agent

最后更新：2026-07-18  
调研范围：实时语音交互模型、Voice Agent 基础设施及 Windows 桌面端落地路线

## 第一章 执行摘要

实时语音 AI 正在从“完成一次语音问答”演进为“持续、自然地参与对话”。产品竞争重点已经从是否具备语音能力，转向响应速度、轮次自然度、重叠语音处理、工具协同、长会话稳定性和隐私成本。

本报告以**端到端语音链路的并发程度**作为统一的技术演进维度，将实时语音交互划分为三个阶段：

1. 串行语音交互：采集、识别、推理、合成和播放依次执行。
2. 流式语音交互：各处理环节通过增量数据并行衔接，但通常仍保持用户与 AI 轮流说话。
3. 全双工语音交互：用户输入与 AI 输出可以持续并发，系统能够理解和处理重叠语音。

“语音原生”不作为第四个并列阶段。串行、流式和全双工描述的是系统运行与交互方式；语音原生描述的是模型架构。全双工既可以由流式 ASR、LLM、TTS 和轮次控制器协同实现，也可以由统一的语音原生模型实现。

截至 2026 年，级联式 Streaming Pipeline 与 Realtime Speech-to-Speech 仍将长期并存：前者在可控性、可观测性、文本审计和工具调用方面具有优势，后者在延迟、韵律和对话自然度方面更具潜力。产品选型不应只追求“更原生”，而应根据业务任务、可靠性要求、隐私边界和成本作出判断。

## 第二章 分类方法与术语

### 2.1 统一演进维度

三个阶段统一回答同一个问题：

> 语音输入链路、理解链路和输出链路能够在多大程度上并发运行？

| 阶段 | 内部处理环节是否重叠 | 用户输入与 AI 输出是否重叠 | 重叠内容是否被持续理解 |
| --- | --- | --- | --- |
| 串行语音交互 | 否 | 否 | 否 |
| 流式语音交互 | 是 | 通常否 | 通常否 |
| 全双工语音交互 | 是 | 是 | 是 |

### 2.2 不参与阶段划分的能力

以下能力可以出现在不同阶段，不应单独作为主阶段：

- 插话打断（Barge-in）：AI 播放时检测到用户明确开口，停止当前生成和播放，并切换到新的用户输入。
- VAD：判断当前是否存在人声。
- 端点检测：判断用户是否已经表达完一个语义轮次。
- 实时转写：在用户说话期间持续显示临时和最终识别结果。
- Tool Calling：模型调用搜索、业务 API 或本地工具。
- 多模态：在语音会话中同时使用文本、图像、屏幕或视频信息。

插话打断通常依赖流式采集、实时检测和可取消播放，但“采用流式处理”并不意味着系统自然具备打断能力。类似地，能够打断也不等于全双工；简单打断只需要切换发言权，全双工则需要理解持续重叠中的语义关系。

## 第三章 技术演进

### 3.1 第一阶段：串行语音交互

经典链路：

```text
用户录音 -> ASR -> LLM -> TTS -> AI 播放
```

上一环节完成后，下一环节才开始。用户输入与 AI 输出完全分离。

优点：

- 架构简单，状态边界清晰。
- 各模块容易替换、测试和审计。
- 适合语音听写、短指令和低频语音入口。
- 用户可以在发送前审核转写文字。

缺点：

- 端到端等待时间较长。
- 长语音必须等待完整录制或上传。
- 对话节奏明显，不适合持续自然交流。
- AI 播放期间通常无法处理新的用户输入。

当前 Windows App 的录音、转写、审核、插入输入框流程属于这一阶段。它首先解决可靠语音输入，而不是直接追求实时语音对话。

### 3.2 第二阶段：流式语音交互

流式链路：

```text
用户边说 -> ASR 边识别 -> LLM 边生成 -> TTS 边合成和播放
```

音频帧、临时转写、模型 Token 和合成音频以增量方式传递，各处理环节在时间上发生重叠。

优点：

- 显著降低首个转写结果和首段回复音频的等待时间。
- 可以实时显示转写、识别状态和端点判断。
- 适合增加插话打断、取消和快速恢复能力。
- 仍保留级联模块的可替换性和可观测性。

缺点：

- 需要处理临时转写修订、音频分块、乱序、背压和取消竞态。
- VAD 或端点判断错误会造成抢答、截断或长时间等待。
- ASR 文字化过程可能损失语气、韵律和非语言信息。
- 用户与 AI 通常仍遵循轮次规则，不等于全双工。

流式语音交互是当前工程落地的重要形态。它既可以只做实时听写，也可以扩展为完整的流式 ASR、LLM、TTS 语音 Agent。

### 3.3 第三阶段：全双工语音交互

全双工链路允许输入与输出持续并发：

```text
用户语音输入  ------------------------>
AI 语音输出       -------------------->
```

系统在 AI 说话期间仍持续理解用户语音，并根据语义和对话状态判断用户是在附和、补充、抢话、纠正还是要求停止。

核心能力：

- 同时监听、理解和生成语音。
- 处理重叠说话，而不是检测到人声后机械停止。
- 区分“嗯”“对”“继续”等附和与真正的轮次抢占。
- 在打断后正确清理旧输出，并保持上下文一致。
- 根据语义动态决定继续说、暂停、停止或改变回答。

主要难点：

- 输入和扬声器输出同时存在时的回声消除与声学反馈。
- 双方重叠语音的识别、归因和上下文合并。
- 打断瞬间已生成、已发送和已播放内容的状态对齐。
- 长时间并发会话中的延迟、成本和一致性控制。

## 第四章 全双工实现路线

### 4.1 系统级全双工

系统级全双工通过多个流式组件和对话控制器协同实现：

```text
音频输入 -> VAD/端点检测 -> 流式 ASR -> LLM -> 流式 TTS -> 音频输出
                \--------- 轮次、打断和会话状态控制 ---------/
```

优势：

- ASR、LLM、TTS 和传输层可以独立选型。
- 文本中间状态清晰，方便审计、检索、工具调用和安全检查。
- 可以复用成熟业务 Agent 和现有文本对话能力。
- 更容易定位延迟和质量问题。

不足：

- 状态控制复杂，组件间存在多处缓冲和取消边界。
- 语音转文字可能丢失部分情绪、停顿和韵律信息。
- 对附和、犹豫和持续重叠的理解通常依赖额外模型或规则。

### 4.2 语音原生全双工

语音原生全双工模型联合建模用户语音、对话状态、回复内容和输出语音，部分方案还让模型直接学习何时听、何时说以及何时停止。

优势：

- 更完整地保留语气、语速、停顿、韵律和情绪。
- 可以直接学习轮次切换、附和和重叠对话模式。
- 减少传统级联中的中间等待和信息损失。

不足：

- 模型内部状态和错误原因更难观察。
- 文本审计、内容安全和工具调用需要额外设计。
- 本地部署对模型、音频编解码和推理资源要求较高。
- 开源模型、评测集和服务框架仍在快速变化。

语音原生全双工是全双工的一种实现路线，不应与串行、流式、全双工三个交互阶段并列。

## 第五章 主流方案调研

### 5.1 OpenAI Realtime API

OpenAI Realtime API 官方说明其原生支持 Speech-to-Speech，并提供文本、图像和音频输入输出。客户端实时语音场景可以使用 WebRTC，服务端场景也可以使用 WebSocket。

公开能力包括：

- 实时语音输入输出。
- 用户插话和回复取消。
- Function Calling 和应用工具接入。
- 音频输入输出转录。
- 会话状态和多模态内容管理。

应注意，官方公开的是 API 能力和使用方式，并未完整披露内部模型结构。因此可以称其为“原生 Speech-to-Speech Realtime 模型”，但不应仅凭 API 行为断言其属于某种论文定义下的单体语音原生架构。

“后台调用更强推理模型”也不是 Realtime API 自动保证的固定能力。更准确的表述是：应用可以通过 Function Calling 将复杂任务交给后台工具、业务服务或其他推理模型，再把结果返回实时会话。

### 5.2 Google Gemini Live API

Gemini Live API 面向低延迟双向语音和多模态会话。官方公开能力包括：

- Barge-in 插话打断。
- Function Calling 和搜索工具接入。
- 输入输出音频转录。
- 原生音频输出。
- 部分模型支持情感对话和主动音频。

具体能力依赖模型版本，情感对话、主动音频、会话时长和上下文限制不能脱离模型说明笼统描述。长时间音频会持续消耗上下文 Token，需要配置上下文压缩和会话恢复策略。

### 5.3 Moshi

Moshi 是开源语音原生全双工研究的重要代表。它并行建模用户和系统两路音频流，并使用 Mimi 流式神经音频编解码器。论文报告的理论延迟约为 160 毫秒，实践延迟约为 200 毫秒。

该数据体现的是模型和实验系统能力，不应直接等同于真实产品端到端延迟。实际产品还需叠加音频采集、网络传输、服务排队、缓冲和设备播放延迟。

### 5.4 BayLing-Duplex

BayLing-Duplex 于 2026 年 6 月发布，探索由单一自回归模型决定何时监听、开始回答和停止回答。其目标是不依赖外部 VAD 或独立轮次控制器完成原生全双工对话。

论文基于公开 GLM-4-Voice 检查点进行训练，并报告了轮次切换、打断和语音回答质量结果。由于发布时间较近，当前结果主要用于观察研究方向，进入生产选型前仍需验证多语言、噪声、工具调用、长会话和真实设备性能。

### 5.5 Pipecat

Pipecat 不是语音模型，而是开源 Voice Agent 框架。它负责把实时传输、VAD、STT、LLM、TTS、Speech-to-Speech 模型和工具调用组织成可运行的 Pipeline。

它适合快速验证多 Provider 组合，并为实时会话、传输和 Agent 编排提供基础设施。模型效果、端到端延迟和生产稳定性仍取决于所选服务、部署位置和应用实现。

### 5.6 LiveKit Agents

LiveKit Agents 是另一套重要的开源实时 Agent 基础设施，支持：

- 基于 WebRTC 的实时音视频传输。
- STT、LLM、TTS 级联 Pipeline。
- OpenAI Realtime、Gemini Live 等直接 Speech-to-Speech 模型。
- Turn Detection、插话处理和工具调用。
- 多 Agent Handoff、SIP 电话接入和服务端调度。

实时语音基础设施调研不应只比较模型，还应比较 Pipecat 与 LiveKit Agents 等框架在传输、会话管理、可观测性、部署和 Provider 适配方面的能力。

### 5.7 DuplexChat

DuplexChat 于 2026 年 7 月发布，是面向全双工语音模型的开源语料和数据构建 Pipeline。它从公开播客中构建说话人分离的双路对话音频，论文报告的数据规模约为 282,634 小时英语和 132,723 小时日语。

它重点解决训练数据中缺少独立说话人音轨和自然重叠对话的问题。它属于数据基础设施，而不是可以直接集成到产品中的实时语音模型。

## 第六章 方案对比与选型

| 方案 | 低延迟潜力 | 对话自然度 | 可观测性 | 工具控制 | 模块替换 | 本地部署难度 |
| --- | --- | --- | --- | --- | --- | --- |
| 串行 ASR + LLM + TTS | 低 | 低 | 高 | 高 | 高 | 中 |
| 流式 ASR + LLM + TTS | 中到高 | 中 | 高 | 高 | 高 | 中到高 |
| 系统级全双工 | 高 | 中到高 | 中 | 高 | 高 | 高 |
| 语音原生全双工 | 高 | 高 | 低到中 | 中 | 低 | 高 |

选型时应优先回答以下问题：

1. 产品是语音输入工具，还是持续语音 Agent？
2. 用户是否必须在发送前审核文字？
3. 工具调用是否需要确定、可追踪和可重放？
4. 音频能否离开设备，是否需要离线运行？
5. 目标首音频延迟、打断延迟和每分钟成本是多少？
6. 是否需要长期保留转录文本，是否允许保留原始音频？
7. 弱网、重连和 Provider 降级时应保持哪些基础能力？

对于任务型桌面应用，流式级联通常是从可靠听写走向实时 Agent 的稳健中间路线。对于陪伴、语言练习、实时访谈等高度依赖语气和轮次自然度的产品，Realtime Speech-to-Speech 或语音原生全双工更具价值。

## 第七章 核心技术挑战

### 7.1 延迟与抖动

低延迟不能只看平均值，还要关注 P50、P95 和 P99。长会话中服务排队、上下文增长、网络波动和音频缓冲都可能造成延迟逐渐恶化。

应分段记录：

- 音频采集和编码延迟。
- 上行网络延迟。
- VAD 与端点判断延迟。
- ASR 首个临时结果和最终结果延迟。
- LLM 首 Token 延迟。
- TTS 首音频延迟。
- 播放缓冲和端到端延迟。

### 7.2 VAD 与端点检测

静音不一定表示用户说完，用户也可能在思考、停顿或自我修正。只使用固定静音阈值容易抢答或等待过久，需要结合声学 VAD、语义端点和业务场景调参。

### 7.3 插话与状态恢复

用户插话时，系统必须同时处理：

- 立即停止本地播放。
- 取消尚未完成的模型生成和 TTS。
- 清空已经生成但尚未播放的音频。
- 记录用户实际听到的内容，而不是模型完整生成内容。
- 将新用户输入与正确的历史上下文合并。

### 7.4 Windows 音频链路

桌面端需要额外处理：

- 麦克风权限和隐私设置。
- 默认设备变化、USB 或蓝牙设备拔插。
- 采样率、声道和编码格式差异。
- AEC 回声消除、降噪和自动增益。
- 睡眠恢复、应用失焦和多应用占用设备。
- 高 DPI、弱性能设备和音频线程稳定性。

### 7.5 工具调用

实时语音 Agent 调用搜索或业务工具时，等待时间可能显著长于普通对话。系统需要提供简短确认、支持取消、避免重复调用，并在工具返回后恢复正确会话状态。

### 7.6 长上下文与会话恢复

长会话需要上下文压缩、记忆分层和重连恢复。系统必须区分实时会话状态、可持久化用户记忆和业务任务状态，不能把无限累积的原始音频或全部转录直接作为长期记忆。

### 7.7 隐私、安全与成本

- 明确音频由本地还是远程 Provider 处理。
- 原始音频默认短期保存并及时清理。
- 日志不得记录密钥、音频正文或完整转录。
- 对流式输入输出实施内容安全和权限控制。
- 统计每分钟成本、并发上限和降级策略。
- 明确语音数据是否用于训练以及服务端保留期限。

## 第八章 评测体系

### 8.1 延迟指标

| 指标 | 定义 |
| --- | --- |
| 首转写延迟 | 用户开始说话到出现首个临时转写的时间 |
| 端点延迟 | 用户实际说完到系统确认轮次结束的时间 |
| TTFA | 用户轮次结束到首段 AI 音频开始播放的时间 |
| 打断停止延迟 | 用户开始有效插话到 AI 音频停止的时间 |
| 工具等待时间 | 发起工具调用到获得可用于回答结果的时间 |

所有延迟指标至少报告 P50、P95 和 P99，不只报告平均值。

### 8.2 交互指标

- 端点准确率与误截断率。
- 误打断率和漏打断率。
- 附和误判率。
- 重叠语音理解准确率。
- 打断后重复回答率和上下文丢失率。
- 30 分钟和 60 分钟长会话一致性。

### 8.3 任务与质量指标

- 中文 CER、英文 WER 和中英混合识别准确率。
- 工具选择、参数生成和最终任务完成率。
- TTS 可懂度、自然度和情绪一致性。
- 事实正确性、角色一致性和安全策略命中率。

### 8.4 鲁棒性与成本指标

- 噪声、回声、快速语速、口音和多人说话。
- 弱网、丢包、重连和 Provider 超时。
- 麦克风切换、系统休眠恢复和设备拔插。
- 每分钟成本、CPU、GPU、内存和网络流量。
- 连续运行后的延迟漂移和资源泄漏。

## 第九章 Windows App 产品落地路线

当前产品决策是先完成完整的串行语音交互，详细范围、模块和验收方式见[串行语音交互完整开发方案](./serial-voice-interaction-development-plan.md)。流式和全双工能力保留为后续技术方向，不进入当前交付范围。

### 9.1 当前基线：可靠的串行语音输入

当前 Phase B 的重点是完整录音、真实 STT、取消、错误恢复和转写审核。该阶段应继续作为可靠基线：

- 用户明确启动录音。
- 实时波纹反映真实音频振幅。
- 停止后执行转写。
- 用户审核和编辑结果后再插入或发送。
- 原始音频按隐私策略及时清理。

这一能力不应因为后续实时语音功能而被移除。对于精确输入、隐私敏感和需要发送前确认的场景，串行听写仍有长期价值。

在当前阶段，还需补齐助手完整回复的整段 TTS、播放控制、输入输出互斥和端到端发布验证，才能把“串行语音输入”升级为“完整串行语音交互”。

### 9.2 后续方向：流式语音输入

在现有 `VoiceRuntime` 和任务生命周期上增加：

- 音频分块上传和背压控制。
- Streaming ASR 临时结果与最终结果。
- 临时转写修订和光标稳定策略。
- VAD、语义端点和手动停止并存。
- 弱网恢复、超时和 Provider 降级。

完成效果是用户说话时即可看到转写，系统能够自动判断一轮语音结束，但仍保留用户审核和发送控制。

### 9.3 后续方向：流式语音回复

在流式输入稳定后增加：

- LLM Token 分块到 TTS 语义片段的调度。
- TTS 首音频快速播放。
- 播放暂停、停止、取消和队列清理。
- 插话打断能力，但不将其定义为独立技术阶段。
- 工具调用期间的等待提示和取消。

该阶段仍可使用级联架构，并通过明确的会话状态机协调采集、生成和播放。

### 9.4 远期方向：全双工验证

建立统一的 `VoiceSession` 或等价会话抽象，在不改写聊天业务层的前提下评估：

- 系统级全双工 Pipeline。
- OpenAI Realtime 或 Gemini Live 等托管 Speech-to-Speech。
- 可行时评估本地或开源语音原生模型。

全双工不应只通过演示效果验收。只有在 TTFA、打断停止延迟、重叠语音理解、工具成功率、长会话稳定性、隐私和每分钟成本均达到目标后，才适合作为默认交互模式。

## 第十章 结论与展望

实时语音 AI 的演进主线可以统一概括为：

```text
串行语音交互 -> 流式语音交互 -> 全双工语音交互
```

串行阶段解决“可靠完成语音任务”，流式阶段解决“尽早处理和响应”，全双工阶段解决“同时听说并理解重叠对话”。语音原生全双工属于第三阶段中的前沿实现路线，而不是独立于全双工之外的第四种交互阶段。

未来产品竞争不仅取决于模型是否能生成自然语音，还取决于整个系统能否在真实设备和长时间会话中稳定管理音频、轮次、工具、上下文、隐私和成本。

对于当前 Windows App，建议从已实现的可靠语音输入出发，先补齐整段 TTS、播放控制和串行回合状态，形成完整的串行语音交互基线。完成并验收该基线后，再评估流式 ASR、流式回复，以及系统级全双工与语音原生全双工。这样的路线能够保留现有工程资产，并用可量化指标决定是否进入下一阶段。
