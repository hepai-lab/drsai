# Windows 应用语音功能总览

最后更新：2026-08-12

## 1. 当前决策

Windows App 同时维护三条独立路线：**串行语音、流式语音、全双工语音**。每条路线都有自己的实施阶段 P1、P2、P3……；路线名称描述交互与并发模型，P 编号只描述该路线内部的成熟度和交付批次。

产品长期保留可靠串行路线，并开始建设独立的全双工路线。`streaming/P2` 停止继续扩展，已有实现暂时冻结为实验资产，不得把全双工状态追加进流式控制器：

- `serial`：可靠、可审核的串行模式，也是默认模式和降级路径。
- `duplex`：使用独立实时语音模型的持续双向会话模式，验收完成前由功能开关控制。
- `streaming`：已有半双工实验模式，暂不作为新的产品主线。

第一阶段串行基线的完整产品闭环是：

```text
用户明确开始录音
-> 完整录音结束
-> 整段语音转写
-> 用户审核并发送
-> 等待助手完整回复
-> 整段文字转语音
-> 用户播放、暂停、继续或停止
-> 回到可录音状态
```

串行模式不同时采集用户语音和播放助手语音，不实现 Streaming ASR、边生成边朗读、插话打断或全双工。

流式语音在保留上述闭环的同时新增：音频分块、临时与最终转写、LLM 正文语义切片、分段 TTS 和有序播放。流式路线仍保持输入输出互斥，不属于全双工路线。

## 3. 路线与阶段定义

### 3.1 三条路线

按照端到端语音链路的并发程度划分：

1. 串行语音交互：录音、STT、聊天回复、TTS 和播放按顺序执行。
2. 流式语音交互：处理环节增量衔接，但用户输入与 AI 输出通常仍不持续重叠。
3. 全双工语音交互：用户输入与 AI 输出持续并发，系统理解重叠语音。

“语音原生”属于全双工的模型实现路线，不作为第四条路线。“插话打断”属于可选交互能力，不作为独立路线。

### 3.2 路线内阶段

每条路线独立使用 P 编号，例如 `serial/P1`、`streaming/P1`、`streaming/P2`、`duplex/P1`。不同路线的同号阶段没有能力等价关系，也不能用全局 P1/P2/P3 代替路线名称。

## 4. 当前实现盘点

### 4.1 已实现

- 麦克风按钮位于输入框底部、“推理”选择器右侧。
- 用户点击后才请求麦克风权限，不进行后台监听。
- 支持麦克风设备选择和 Auto、中文、英文语言提示。
- 使用 `MediaRecorder` 录制完整音频。
- 使用 `AudioContext` 和 `AnalyserNode` 绘制真实振幅波纹。
- 静音时波纹保持平直；新采样从右侧进入，历史采样向左移动。
- 停止录音后合并完整音频 Blob，再提交整段转写。
- Renderer、Preload、Main 使用类型化语音 API。
- 使用二进制 `Uint8Array` 传输，不再使用 Base64 音频契约。
- Main 提供请求 ID、任务注册、取消、超时、有限重试和单一终态。
- Main 校验音频大小、时长、MIME 和文件签名。
- 临时音频使用随机文件名、短 TTL，并在终态清理。
- `gateway-provider` 调用受认证的 `/v1/audio/transcriptions`。
- `fixture` Runtime 支持无网络的确定性开发和测试。
- 转写完成后进入可编辑审核状态，不自动发送。
- 支持插入原光标位置、重试、丢弃和 Provider 披露。
- 可选把已审核转写写入 `.drsai/voice-context.json` 并通过 `voice-input` 导入。

### 4.2 部分实现或需要加固

- 采集、波纹和审核逻辑仍集中在 `ChatWorkspace.tsx`，职责过重。
- 现有状态只覆盖录音和转写，没有覆盖完整语音回合。
- 设备拔出、睡眠恢复、应用失焦和多窗口竞争需要系统验证。
- 语言和设备偏好主要是组件状态，尚缺稳定的语音设置契约和迁移策略。
- 现有验证脚本较多是契约或源码结构检查，真实组件行为和资源泄漏测试仍需补充。
- Provider Live Smoke 和 Windows 安装包真机麦克风测试依赖发布环境执行。

### 4.3 尚未实现

- 串行语音会话控制器和输入、输出互斥规则。
- 助手消息 TTS Runtime 契约。
- 系统声音和 Provider TTS 适配器。
- TTS 合成任务、取消、缓存和临时文件清理。
- 助手消息朗读、暂停、继续、停止、语速和声音选择。
- 助手回复完成后的可选自动朗读。
- 录音、聊天生成、TTS、播放之间的端到端状态与错误恢复。
- 完整串行语音回合的自动化和安装包验收。

## 6. 串行路线 P1 完成标准

只有同时满足以下条件，才能将串行语音交互标记为完成：

- 用户可用语音完成一次输入，审核后发送，并收到文本回复。
- 完整助手回复可以通过至少一个生产可用 TTS Runtime 合成为语音。
- 用户可以播放、暂停、继续和停止回复语音。
- 自动朗读默认关闭，只能由用户主动开启。
- 录音与播放严格互斥，不存在麦克风和助手音频同时活动。
- 任一阶段失败后都能恢复到可输入状态，且不丢失原输入和已生成文字。
- 麦克风、临时音频、TTS 音频、任务、定时器和事件监听均可证明被清理。
- 用户能够知道 STT 和 TTS 是本地处理还是发送给 Provider。
- 标准 CI 不依赖真实外部服务；发布前完成 Provider 和 Windows 安装包 Smoke。
- 完整验收矩阵及发布门禁全部通过。

## 7. 非当前范围

- Streaming ASR 和临时转写。
- 自动语义端点检测。
- LLM Token 到 TTS 的增量合成。
- AI 说话期间监听用户麦克风。
- 插话打断和重叠语音理解。
- Realtime Speech-to-Speech。
- 全双工或语音原生模型。

这些能力必须在串行阶段完成并形成稳定基线后，重新立项和评审。
