# 串行语音开发方案 P2：一键闭环

> 文档状态：已实施，自动化验收通过；物理设备矩阵待人工签署
> 适用产品：OpenDrSai Windows App
> 阶段定位：在现有串行语音基础组件和模型能力之上，完成可交付的一键语音回合
> 不包含：流式 ASR、边生成边朗读、自动端点检测、插话和全双工交互

## 1. 阶段目标

P2 的目标是把当前已具备的录音、ASR、聊天和 TTS 组件连接成默认可用的串行语音闭环。

用户主流程：

```text
点击麦克风
-> 开始录音并显示真实音量波纹
-> 再次点击停止
-> 自动调用 ASR
-> 将最终转写写入普通输入框
-> 用户编辑或直接发送
-> 等待模型生成完整回复
-> 用户点击该消息的“朗读”按钮
-> TTS 合成并播放该条消息
```

本阶段成功的核心标准是：用户通过一次开始、一次停止完成语音输入，默认可在发送前检查和修改最终转写；获得回复后，可以明确选择朗读任意一条完整助手消息。

## 2. 当前基础

现有实现已经具备以下能力：

- 输入栏麦克风入口、录音状态和真实音量波纹。
- 基于 `MediaRecorder` 的音频采集、设备选择和权限错误处理。
- 智能体级 ASR、LLM、TTS 模型绑定。
- `whisper-1` ASR 和 `tts-1` TTS 的真实 Provider 调用能力。
- Provider 凭据安全存储和 Gateway 路由。
- 语音回合状态机、取消和错误状态。
- 助手消息朗读、暂停、继续和停止的基础组件。
- ASR、TTS、录音、播放、IPC 和真实 Provider 测试脚本。

实施前的默认路径是：

```text
录音 -> ASR -> 审核转写 -> 插入输入框 -> 手动发送
```

因此，P2 的主要增量不是重新实现底层模型调用，而是完成自动提交、消息关联、逐消息朗读和端到端可靠性收敛。

## 3. 产品边界

### 3.1 本阶段包含

- 点击开始、点击停止的整段录音交互。
- 停止录音后自动执行整段 ASR。
- ASR 成功后默认进入最终转写确认，用户确认后发送；设置中可选择自动发送。
- 等待并关联该回合的完整助手回复。
- 用户点击助手消息后进行整段 TTS 和播放。
- 录音、聊天、合成和播放之间的串行仲裁。
- 失败恢复、任务取消、隐私清理和真实链路验收。

### 3.2 本阶段不包含

- 自动静音检测和自动停止录音。
- 录音过程中展示临时转写。
- LLM 生成过程中分段合成和播放。
- 用户说话与助手播放同时进行。
- 插话、打断理解和全双工会话。
- 默认自动朗读助手回复。

## 4. 交互规则

1. 第一次点击麦克风开始录音，第二次点击停止录音。
2. 停止录音后立即进入识别状态，按钮和状态区域必须提供明确反馈。
3. ASR 返回非空最终文本后，默认写入普通输入框，不展示独立审核卡片或 Provider 提示。
4. ASR 为空、失败、超时或被取消时不得创建用户消息。
5. 录音开始前若正在播放语音，先停止当前播放，再打开麦克风。
6. 助手消息必须完整生成后才显示可用的朗读操作。
7. 点击一条消息的朗读按钮，只能朗读该条消息，不得错误朗读最新消息。
8. 同一时间最多存在一个录音任务、一个 ASR 任务、一个聊天生成任务和一个播放任务。
9. 默认启用“发送前确认转写”；用户可在设置中关闭并切换为自动发送。
10. 自动发送必须复用普通文本消息的提交入口，不建立独立聊天发送实现。

## 5. 状态模型

### 5.1 语音输入回合

默认转写草稿链路：

```text
idle
-> requesting_permission
-> recording
-> preparing_audio
-> transcribing
-> 将转写插入普通输入框
-> idle
```

可选路径：

- `transcribing -> ready_to_send -> submitting -> awaiting_response`：仅用于用户主动关闭“发送前确认”的自动发送模式。
- 任一活动状态均可进入 `cancelling -> completed`。
- 任一执行阶段失败均进入 `failed`，用户可重试或回到 `idle`。

### 5.2 消息朗读

```text
idle -> synthesizing -> playing -> completed
                         |  ^
                         v  |
                       paused
```

录音与播放互斥：

- `recording` 开始时停止 `synthesizing`、`playing` 或 `paused`。
- 播放开始时不得存在录音或 ASR 任务。
- 聊天仍在生成时，当前消息的朗读按钮不可用。

## 6. 开发模块

### M1 一键录音入口与回合控制

功能点：

- 第一次点击开始录音，第二次点击停止并进入识别。
- 麦克风图标、停止图标、波纹和状态文字保持一致。
- 防止快速重复点击创建多个 `MediaRecorder`。
- 录音开始时停止已有 TTS 和音频播放。
- 页面切换、窗口关闭、设备断开时安全取消录音。

验收方式：

- 模拟点击后，状态依次进入 `requesting_permission` 和 `recording`。
- 第二次点击后，只生成一份音频并进入 `preparing_audio`。
- 连续点击 50 次，最多存在一个活动录音任务。
- 录音期间波纹仅由真实音频采样驱动，静音时接近噪声底线。
- 切换会话或关闭页面后，麦克风轨道全部停止。

### M2 ASR 自动识别与确认提交

功能点：

- 停止录音后自动提交整段音频到智能体绑定的 ASR 模型。
- 只接受 ASR 最终结果，不使用临时文本触发发送。
- 最终转写非空时默认进入审核，用户确认后进入聊天提交；关闭确认设置时可直接提交。
- 空音频、空转写和无有效语音不得发送。
- 保留原始转写结果用于失败恢复，但不写入普通诊断日志。

验收方式：

- 输入固定音频后，ASR 只调用一次。
- ASR 成功后普通输入框显示完整转写，不出现额外按钮和说明文字；点击普通发送按钮后聊天区出现用户消息。
- 关闭“发送前确认转写”后，ASR 成功可自动发送，用于验证可选兼容模式。
- ASR 返回空文本时，用户消息数量不变。
- ASR 超时、认证失败、限流和断网时均不误发送。
- 取消 ASR 后，迟到的结果不能触发聊天提交。

### M3 输入框、附件与普通发送入口协调

功能点：

- 明确录音前已有文字与转写文本的组合规则。
- 默认规则：输入框为空时填入转写；输入框非空时在原光标位置插入转写，之后由用户正常编辑或发送。
- 普通发送与可选自动发送都复用 `submitWithAttachments` 或其稳定领域入口。
- 保持已选择的附件、技能、模型和推理等级。
- 成功发送后清空本次输入；失败时恢复可编辑文本和附件。

验收方式：

- 分别验证空输入、句首、句中、句尾和选中文本五种位置。
- 携带图片或文件时，普通发送与可选自动发送都包含原附件。
- 提交失败后输入内容、附件和转写文本不丢失。
- 普通键盘发送与语音发送产生相同的聊天请求结构。
- 普通发送和可选自动发送均不得产生重复用户消息。

### M4 语音回合与助手回复关联

功能点：

- 为每个语音回合记录 `turnId`、ASR 请求、用户消息、聊天请求和助手消息。
- 用户消息提交成功后进入 `awaiting_response`。
- 只在对应助手消息完整结束时进入 `response_ready`。
- 取消、重试、重新生成和切换会话时不得关联到错误消息。
- 回复失败不影响已发送用户消息，可从聊天层重试。

验收方式：

- 连续执行两个语音回合，每个回合关联到正确的助手消息。
- 在语音回合之间插入普通文本消息，消息关联仍正确。
- 回复流中断时状态进入失败，不错误标记 `response_ready`。
- 切换会话后，旧会话迟到事件不能改变新会话状态。
- 重新生成回复时，只更新目标消息的朗读可用状态。

### M5 助手消息逐条朗读

功能点：

- 每条已完成且有可朗读正文的助手消息显示朗读按钮。
- 点击后使用智能体绑定的 TTS 模型合成该条消息。
- 支持播放、暂停、继续和停止。
- 同一时间只允许一条消息处于合成或播放状态。
- 再次点击其他消息时，先停止当前播放，再朗读新消息。
- Provider TTS 失败时提供重试和切换 Windows 本地朗读的恢复操作。

验收方式：

- 点击历史中的任意助手消息，只朗读该条消息正文。
- 正在生成、错误或空内容消息不提供可用朗读按钮。
- 快速点击两条消息不会发生双重播放。
- 暂停后播放位置保持，继续后从原位置恢复。
- 停止后释放音频对象、临时文件和合成任务。
- `tts-1` 真实合成结果具有正确音频 MIME、签名和非零时长。

### M6 串行仲裁与错误恢复

功能点：

- 统一管理录音、ASR、聊天、TTS 和播放的互斥关系。
- 错误按麦克风权限、设备、空音频、认证、网络、限流、超时、Provider、播放分类。
- 每个错误提供适合的重试、取消、打开设置或切换运行时操作。
- 重试必须复用原回合上下文，不重复发送已成功的阶段。
- 应用休眠、恢复、网络变化和输出设备变化后状态可恢复。

验收方式：

- 为每种错误代码执行单元测试和 UI 恢复测试。
- ASR 已成功而聊天失败时，只重试聊天，不重新上传录音。
- TTS 失败不改变聊天消息内容和语音输入回合结果。
- 录音期间点击朗读不可启动播放；播放期间点击录音会停止播放。
- 取消后所有异步迟到事件均被忽略。

### M7 隐私、资源和诊断

功能点：

- 仅在用户点击麦克风后请求和采集音频。
- 临时音频按任务生命周期删除，并有过期清理兜底。
- 诊断只记录阶段、耗时、字节数、模型引用和错误代码。
- 不记录原始音频、完整转写、完整回复和 Provider 凭据。
- 为完整回合建立统一 trace，但不跨会话泄漏正文。

验收方式：

- 正常、失败、取消和进程退出后扫描临时目录，无录音残留。
- 扫描诊断日志，不出现测试音频字节、完整测试转写或 API Key。
- 凭据仅由 Gateway 解析，Renderer 和普通 IPC 响应不包含凭据引用。
- 20 回合后任务注册表、MediaStream、Audio 和临时文件数量回到基线。

### M8 自动化、真实 Provider 与真机验收

功能点：

- 建立模拟组件、Main/Preload IPC、真实 Provider 和真机四层测试。
- 自动模拟点击、麦克风输入、ASR、聊天回复、TTS 和浏览器播放。
- 使用真实 `whisper-1`、聊天模型和 `tts-1` 执行完整回合。
- 在打包应用中验证与开发模式一致的行为。
- 完成 Windows 11 内置麦克风和默认扬声器验收。

验收方式：

- 自动链路必须覆盖：

```text
点击开始
-> 模拟音频输入
-> 点击停止
-> ASR 完成
-> 转写进入普通输入框
-> 点击普通发送按钮
-> LLM 完整回复
-> 点击朗读
-> TTS 完成
-> 音频播放结束
```

- 必须记录并断言以下状态：

```text
requesting_permission
recording
preparing_audio
transcribing
submitting
awaiting_response
response_ready
synthesizing
playing
completed
```

- 真实测试要求 ASR 文本非空、LLM 回复非空、TTS 音频非空且可以播放。
- 连续执行 20 个真实或授权回合，不得重复发送、串错消息或泄漏临时资源。
- Windows 11 真机完成内置麦克风录音和默认扬声器朗读。

## 9. 完成标准

P2 只有同时满足以下条件才可标记完成：

- 用户通过开始和停止两次点击完成一次语音输入。
- 停止后自动执行 ASR，并自动创建且只创建一条用户消息。
- 模型返回的完整助手回复与本次语音回合正确关联。
- 用户点击回复的朗读按钮后，可以听到对应消息内容。
- 空录音、ASR 失败、聊天失败、TTS 失败和播放失败均不会导致误发送或数据丢失。
- 普通文本输入、附件、技能和模型选择在语音发送中保持一致。
- 完整模拟 E2E、真实 ASR/LLM/TTS、打包应用和 Windows 11 真机验收通过。
- 连续 20 回合无重复消息、错误消息关联、资源泄漏和隐私日志泄漏。

## 10. 后续阶段关系

P2 完成后，Windows App 将具备稳定的串行语音一键回合。后续如进入流式语音阶段，应在不破坏本方案默认串行路径的前提下并行增加：

- 音频分块上传。
- 临时与最终转写。
- LLM 回复语义切片。
- 分段 TTS 和有序播放。

串行模式继续作为精确输入、失败降级和发布回归的稳定基线。
