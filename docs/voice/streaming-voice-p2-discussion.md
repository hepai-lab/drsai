# Windows 流式语音路线 P2 讨论稿

最后更新：2026-08-10

技术路线：`streaming`

路线阶段：P2

前置基线：[流式语音路线 P1 完整开发方案](./streaming-voice-interaction-development-plan.md)

## 1. 定位

`streaming/P2` 是流式路线自身的第二个实施阶段，不是“第二条路线”，也不是全双工前身的别名。它继续保持用户输入与 AI 输出互斥，不实现持续重叠语音理解。

P1 已建立双模式、流式 ASR、LLM 语义切片、分段 TTS、有序播放、取消与确定性 Fixture。P2 的主题是把低延迟闭环提升为更自适应、更稳定、可恢复且可运营的生产能力，并让用户讲话期间的 partial/final 以安全的投影方式实时出现在 Composer 内，再利用同段后文和有界对话上下文生成可撤销的修复建议。

## 2. 候选目标

1. 自适应端点：结合语言、噪声、语速和停顿动态调整 VAD/endpoint 阈值，降低截断与尾部等待。
2. 会话复用：复用 Provider 长连接、预热模型与音频链路，降低跨回合首包延迟。
3. 断线恢复：定义重连、事件游标、去重、补发和可见降级语义。
4. 自适应缓冲：根据网络抖动和 TTS 生成速率调整预取水位，在低延迟与卡顿率之间取平衡。
5. 质量策略：按延迟、质量、成本和 Provider 能力选择模型、切片与回退路径。
6. 多 Provider 能力层：通过共享能力接口接入更多 Runtime，但保持流式路线自己的会话控制。
7. 可运营性：补齐分阶段延迟、修订率、端点误差、卡顿率、重连率和每分钟成本 SLO。
8. 生产验证：扩大长会话、弱网、设备、语言、缩放和安装包矩阵。
9. 代码边界：完成 `serial/streaming/shared` 显式目录迁移和禁止跨路线内部导入的门禁。
10. 实时 Composer：稳定前缀与临时后缀分层显示，不破坏光标、选择区和 IME。
11. 上下文修复：结合后续语音、对话摘要、用户词典和工作区术语消歧，展示差异并允许撤销。

## 3. 明确不属于 P2 的能力

- AI 播放期间持续监听并理解用户讲话。
- 插话后的重叠语义归因、发言权仲裁和双向并发状态机。
- 回声消除闭环、双路音频同步和原生 Speech-to-Speech 双工会话。

这些能力属于 `duplex/P1` 的范围；不能通过向流式控制器追加条件分支实现。

## 4. 建议的 P2 主线

建议以“可靠性与恢复 + 自适应延迟”为主线，多 Provider 抽象作为基础设施，不把增加 Provider 数量本身当作交付结果。验收重点应是：弱网和长会话下不丢终态、P95 首转写/首音频改善、卡顿率下降、串行与流式 P1 零回归。

## 5. 待确认的产品决策

1. P2 首要价值排序：更低延迟、弱网稳定、长会话，还是多 Provider。
2. 首批生产 Provider 与协议约束。
3. 自动 endpoint 是否直接发送，还是仍进入用户审核。
4. 会话复用的空闲时长、隐私提示与成本上限。
5. 允许的自动回退范围：同 Provider 重连、切 Provider，或提示切回串行。
6. P95 首转写、首音频、卡顿率和恢复时间的目标阈值。
