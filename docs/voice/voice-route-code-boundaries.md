# Windows 语音三路线代码边界

最后更新：2026-08-10

## 1. 架构决定

串行、流式和全双工是三条独立技术路线；P1、P2、P3……是每条路线内部的实施阶段。代码采用“路线核心隔离、共享能力下沉、产品入口组合”的结构。

目标目录如下：

```text
apps/desktop/windows/src/
  shared/voice/
    contracts/              # 跨进程 DTO、错误、能力和公共接口
  main/voice/
    shared/                 # Provider 中立基础设施、校验、诊断、设备能力
    serial/                 # 串行 Runtime、任务和会话生命周期
    streaming/              # 流式 Runtime、传输、背压和增量队列
    duplex/                 # 全双工 Runtime、重叠仲裁和回声处理
  preload/voice/
    shared/
    serial/
    streaming/
    duplex/
  renderer/src/voice/
    shared/                 # 波形、设备偏好、无障碍控件和纯音频工具
    serial/                 # 串行状态机、Hook 和控制器
    streaming/              # 流式状态机、Hook、切片器和播放队列
    duplex/                 # 全双工状态机、仲裁和双向会话 UI
```

测试目录镜像产品目录；每条路线拥有独立的单元、IPC、集成、E2E 和发布门禁。

## 2. 依赖规则

1. `serial`、`streaming`、`duplex` 的核心代码不得直接导入另一条路线的内部文件。
2. 路线核心只能依赖同路线代码、平台通用代码和 `voice/shared` 的公开契约。
3. 模式选择与降级发生在产品组合层，不在任一路线控制器里散布另一条路线的条件分支。
4. 如果一段实现需要被两条路线使用，先提炼为无路线状态、无路线策略的共享接口或基础设施，再由各路线引用。
5. Provider 专用适配器可以实现共享接口；包含路线语义的适配器必须留在对应路线目录。
6. 路线间切换必须经过公开入口并结束当前会话，不能共享可变的回合状态。

## 3. 可以与不可以复用的内容

适合共享：DTO 与错误码、设备枚举、权限检查、音频格式与签名校验、诊断埋点、日志脱敏、Provider 中立客户端、纯 PCM 工具、视觉组件和设计令牌。

必须分开：回合状态机、会话控制器、取消语义、端点策略、流量控制、播放编排、重连与恢复策略，以及全双工的发言权仲裁、回声消除和重叠语音理解。

## 4. 阶段与目录的关系

P 编号不创建横向共享核心。例如 `streaming/P2` 继续演进 `streaming/`，不会迁入 `duplex/`；出现持续输入输出重叠、重叠语义理解或回声闭环时，应在 `duplex/P1` 建立独立核心。

每条路线的 P 阶段应通过能力开关、内部版本或发布配置演进，避免复制 `p1/`、`p2/` 目录。只有需要长期并行对比的算法实现才保留版本化适配器，并由该路线的统一接口选择。

## 5. 当前状态与渐进迁移

当前 Main 侧流式核心已在 `src/main/voiceStreaming/` 独立存在，串行核心仍分布在 `src/main/voice.ts`、`voiceTts.ts` 等文件。后续按以下顺序迁移，不做一次性大搬家：

1. 先冻结公开契约和现有串行/流式回归门禁。
2. 建立 `voice/shared`，只移动已证明为路线无关的纯能力。
3. 把串行与流式核心分别迁入显式目录，保持兼容导出，确保调用方无需同步重写。
4. 跑完两条路线的全套自动化、打包应用 Fixture 和真机矩阵后，再删除旧兼容入口。
5. 全双工开始实施时直接建立 `duplex/`，不得以修改流式状态机的方式偷渡全双工语义。
