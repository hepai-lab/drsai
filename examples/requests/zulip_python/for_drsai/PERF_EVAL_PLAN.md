# Zulip Bridge 优化前后性能评估方案

用于量化 [PERF_FIX_PLAN.md](./PERF_FIX_PLAN.md) 中各项优化的实际收益。核心思路：在**相同负载**下，对**优化前（baseline）**与**优化后（optimized）**两个版本采集同一组指标进行对比。

---

## 一、核心指标

### 1. 并发吞吐（最能体现 P0-1 的收益）

| 指标 | 定义 | 优化前预期 | 优化后预期 |
|---|---|---|---|
| **吞吐量 (QPS)** | 单位时间成功处理的消息数 | ≈ 1 / 单请求耗时（串行） | ≈ N × baseline（N=并发数） |
| **有效并发数** | 同时在处理中的请求数 | 恒为 1 | 接近线程池上限 |
| **队头阻塞时延** | 后到消息因前序占用而多等的时间 | 高（∑前序耗时） | ≈ 0 |

> 这是串行→并发改造最直接的体现，单用户基准下看不出来，**必须多并发压测**。

### 2. 端到端时延（Latency）

延迟需分位统计，平均值会掩盖长尾。

| 指标 | 定义 | 说明 |
|---|---|---|
| **首字时延 (TTFT)** | 用户发消息 → 占位/首个 chunk 出现 | 受队头阻塞影响最大 |
| **完成时延** | 用户发消息 → 最终回复定稿 | 端到端总耗时 |
| **P50 / P95 / P99** | 各时延的分位数 | 并发优化主要改善 P95/P99 长尾 |

### 3. 内存占用（体现 P1-1）

| 指标 | 定义 | 采集方式 |
|---|---|---|
| **常驻内存 (RSS)** | 进程实际占用物理内存 | `psutil.Process().memory_info().rss` |
| **会话数 `len(_store)`** | 当前维护的会话条目数 | 直接读 `Conversations._store` |
| **内存增长斜率** | 长时间运行下 RSS 随时间的增长率 | 应从"持续上涨"变为"趋于平稳" |

### 4. 稳定性 / 可用性（体现 P0-2）

| 指标 | 定义 | 说明 |
|---|---|---|
| **错误率** | 失败请求 / 总请求 | 后端异常时优化后应隔离单请求，不冻死全局 |
| **冻结恢复时间** | 后端挂起后 bot 恢复响应的耗时 | 优化前 = ∞（永久冻结）；优化后 ≈ timeout 值 |
| **超时释放率** | 超时请求中线程正确释放的比例 | 应为 100% |

### 5. 下游 API 效率（体现 P2-1）

| 指标 | 定义 | 说明 |
|---|---|---|
| **`update_message` 调用次数/回复** | 单条回复触发的 Zulip 编辑 API 数 | 优化后应下降 |
| **Zulip 限流命中次数** | 触发 rate limit 的次数 | 应趋近 0 |

---

## 二、测试场景设计

| 场景 | 负载 | 主要观测指标 |
|---|---|---|
| **S1 单请求基准** | 1 用户 1 条消息 | 完成时延、TTFT（建立基线） |
| **S2 并发压测** | N=5/10/20 用户同时发消息 | 吞吐量、P95/P99 时延、队头阻塞 |
| **S3 长稳运行** | 持续低频发消息 + 制造大量不同 topic，运行 ≥1h | RSS 增长斜率、会话数 |
| **S4 后端故障注入** | 指向不可达/挂起的后端 | 冻结恢复时间、错误率、超时释放率 |
| **S5 长回复流式** | 触发一条 ≥60s 的长回复 | `update_message` 调用次数 |

---

## 三、对比方法

1. **固定变量**：相同后端、相同模型、相同消息内容/长度、相同机器。
2. **两版本对照**：
   - baseline：优化前 commit
   - optimized：优化后 commit
3. **多次取样**：每个场景重复 ≥5 次，报告均值 + 分位数，避免偶发抖动。
4. **结果呈现**：每个指标给出「优化前 / 优化后 / 提升倍数或百分比」三列对比表。

---

## 四、采集工具建议

| 维度 | 工具/方法 |
|---|---|
| 时延 / 吞吐 | 自写压测脚本（`asyncio` 或 `ThreadPoolExecutor` 并发发消息，记录时间戳） |
| 内存 | `psutil` 周期采样 RSS，或 `tracemalloc` 定位增长点 |
| API 调用计数 | 在 `update_message` / `create` 处加计数器或日志埋点 |
| 故障注入 | 临时把 `DRSAI_BASE_URL` 指向 `sleep` 服务或不可达地址 |

> 压测脚本可放在 `eval/harness_eval/` 下，与本评估方案配套。

---

## 五、验收标准（建议目标）

| 指标 | 目标 |
|---|---|
| 并发吞吐 (N=10) | ≥ baseline 的 5× |
| P95 完成时延 (N=10) | 较 baseline 下降 ≥ 60% |
| 后端挂起恢复时间 | 从 ∞ 降至 ≤ timeout + 5s |
| 长稳运行内存 | RSS 增长斜率趋于 0，会话数受 `MAX_SESSIONS` 约束 |
| 单条长回复 update 次数 | 较 baseline 下降 ≥ 30% |

---

## 六、指标 ↔ 优化项映射

| 优化项 | 验证指标 | 测试场景 |
|---|---|---|
| P0-1 并发 | 吞吐量、队头阻塞、P95/P99 | S2 |
| P0-2 超时 | 冻结恢复时间、超时释放率 | S4 |
| P1-1 内存淘汰 | RSS 斜率、会话数 | S3 |
| P1-2 历史轮数 | 实际保留轮数（功能正确性） | S1 |
| P2-1 编辑频率 | update_message 次数、限流命中 | S5 |
