## Current Verified Slice

- Slash command registry and parser are centralized in `src/renderer/src/chatCommands.ts`.
- Commands execute locally and never call the gateway or external services.
- `/fix`, `/test`, `/commit`, `/compact`, and `/memory` are now registered as read-only local intent/context commands; `/skills` additionally opens Skills Square as a workflow selection bridge and can focus a specific skill or workflow template from command arguments.
- The composer shows a command panel as soon as the user types `/`.
- Command output is appended to the active thread as a normal user/assistant pair, so it is visible and persisted with the current chat snapshot.
- `/model <alias>` and `/agent <id-or-name>` resolve against the loaded model/agent catalogs and update the composer selector without calling the gateway.
- `/fork <intent>` keeps fork runtime-mode metadata, creates an isolated Git worktree under the desktop data directory, creates a local `agent_run` fork thread pointing at that worktree, persists source/worktree/branch/base metadata on the thread, then switches the UI to that thread while leaving an audit message in the source thread; `/fork queue <task1; task2>` parses a bounded task list, creates one isolated fork-backed `agent_run` thread per queued subtask, stores queue group/index/status metadata, accepts optional `@agent` prefixes for per-subtask dispatch assignment, requests Approval Center review before the queue can start, and reports waiting/ready/blocked queue state in the source thread and thread list; `/fork dispatch` finds approved ready queue threads for the current workspace, forwards selected agent/model metadata, honors per-thread agent assignments when present, starts each as an agent run in its isolated worktree, and persists running/completed/blocked queue state; `/fork schedule [limit N]` scans the current workspace for approved ready queue threads, orders them by queue group/index/update time, preserves per-thread agent assignments, and reuses the same dispatch path without bypassing queue-start approval; later chat/terminal/files actions derive their workspace from the active fork thread so they stay on the isolated worktree, and thread-menu merge-back/discard lifecycle requests enter Approval Center before approved merge-back or controlled cleanup execution. Approved cleanup now applies an explicit branch policy: merged branches are deleted safely with `git branch -d`, while unmerged discarded branches are archived under `drsai/archive/...`.
- `/plan`, `/goal`, `/review`, `/fix`, `/test`, `/commit`, and `/fork` set a first-class runtime mode visible in the composer until cleared.
- Fork threads are marked in the thread list, and their context menu exposes copyable fork details, source path, branch, isolated worktree path, lifecycle state, lifecycle execution messages, branch cleanup/archive results, inline conflict workbench state, and merge-back/discard lifecycle approvals routed through Approval Center.
- Active runtime mode is sent with natural-language requests as `metadata.runtime_mode` and as a system runtime-mode instruction.
- The legacy Python SSE gateway accepts `metadata.runtime_mode`, whitelists known mode names, and prefixes the agent task with backend mode instructions so the runtime mode affects the downstream planning/review/fix/test/commit/goal/fork behavior.
- The composer shows a context assembly preview before send, covering visible attachment chips and workspace instructions.
- `/mention selection <text>` creates a visible manual @selection context chip that is queued for the next natural-language message and then cleared with other explicit context.
- `/mcp prompt <name> <text>` creates a visible reviewed MCP prompt context chip for the next natural-language message, `/mcp sync [server]` queues Approval Center permission for bounded stdio live MCP enumeration from `.drsai/mcp-servers.json` into `.drsai/mcp-context.json`, and `/mcp resource [selector]` / `/mcp tool [selector]` imports reviewed MCP resource/tool handoff context from that file into visible chips. `/mcp exec <server> <tool> [json]` queues a separate MCP tool execution approval; approved execution performs bounded stdio `tools/call` with `shell: false`, then writes the reviewed result back into `.drsai/mcp-context.json` for explicit `/mcp tool` import.
- The desktop bridge reads a bounded `.drsai/ide-context.json` handoff inside the active workspace and exposes IDE current file/current-selection context through the same visible file and selection attachment chips.
- A source-controlled VS Code producer under `editor-integrations/vscode` listens for active editor, selection, and active-document edits, writes the current file and bounded selection into the same workspace-local handoff file, and is covered by `npm run verify:vscode-ide-producer`.
- JetBrains/Visual Studio producer skeletons under `editor-integrations/jetbrains` and `editor-integrations/visual-studio` share the same `.drsai/ide-context.json` schema, source tags, workspace-boundary checks, selection limits, temp-file replace semantics, packaged install preflight commitments, and manual desktop attach instructions; covered by `npm run verify:ide-producers`.
- The composer estimates context size for each visible source, aligns the aggregate budget with selected model `token_limit` / `max_tokens` when available, optionally calibrates the estimate from bounded model-catalog tokenizer samples, reserves output tokens, shows a fallback budget when model limits are unknown, and displays the aggregate budget state before submit.
- The permission boundary has a typed shared execution policy covering chat model calls, browser reads/interactions, workspace diff/stage/revert, terminal writes, shell commands, commits, network, and external services.
- `/permissions` exposes the current git commit policy; `/commit <message>` runs a staged-diff preflight, captures the most recent terminal test/verification result for the workspace when available, blocks empty staged commits, queues a `git.commit` approval proposal for the selected workspace with the preflight detail and structured staged-file checklist, requires local review confirmation in Approval Center, and only executes `git commit` from the main process after approval.
- `/memory add <note>` persists workspace-scoped project memory under the desktop data directory, `/memory edit <index|id> <note>` updates one entry, `/memory delete <index|id>` removes one entry, `/memory retrospective <note>` captures a post-task lesson, `/memory` lists the current workspace's reviewable memory, `/memory clear` removes all entries, and later natural-language chat includes recent project memory as an explicit system section.
- `/command add <name> = <prompt>` persists workspace-scoped reusable prompt templates under the desktop data directory, `/command` lists them, `/command delete <name>` removes them, and direct `/<custom> [args]` invocation expands the template back into the composer for review instead of auto-sending. Templates support `{{args}}`; args are appended under an Arguments section when the placeholder is absent.
- Skills Square now includes a workspace-scoped Project Memory review panel for listing, adding, editing, deleting, saving retrospectives, marking entries as skill-promotion candidates, generating reviewable `SKILL.md` skill draft files from memory entries, and installing reviewed drafts into a safe local desktop skills directory.
- Skills Square now includes a Workflow Marketplace section with starter templates for plan/review/fix, test/commit, memory-to-skill, and connector digest workflows, including triggers, steps, approval requirements, risk, verification commitments, and approval-gated workflow run recipe preparation for available templates.
- Workflow run preparation now returns a structured recipe with chat commands, manual review checkpoints, terminal verification commitments, and Approval Center queue status; `test-and-commit` routes through the shared `workflow.run` approval policy before it is considered ready.
- Prepared workflow recipes can now be started into a durable workspace-scoped run queue under `DRSAI_HOME/desktop/workflow-runs.json`, exposing per-step execution state for chat commands, terminal commands, manual checkpoints, and Approval Center follow-up without bypassing the existing approval boundaries.
- Workflow run steps now expose a dispatch hook: chat-command steps are sent into the chat composer through a renderer event and marked complete in the durable run store, manual checkpoints can be marked complete, and terminal-command steps return the command with an explicit instruction to use the existing terminal approval path rather than writing to a pty directly.
- Workflow chat command steps dispatch into the chat bar, and workflow terminal command steps dispatch into the terminal proposal drawer, where the existing command risk preview and shell approval path still control execution; Approval Center shell approval marks the terminal workflow step as running, and terminal command completion calls back into the workflow run store and advances the run on exit code 0 or blocks it on non-zero exit.
- A durable workspace-scoped background task queue persists under the desktop data directory, mirrors workflow run start/running/waiting/completed/blocked states, and appears in Skills Square as a Background tasks status panel with source, current step, message, and verification commitment.
- A durable workspace-scoped scheduled/monitor definition store persists under `DRSAI_HOME/desktop/scheduled-tasks.json`, exposes main/preload/mock API methods for list/create/update/run-due, and appears in Skills Square with cadence, target, approval, pause/enable, due-scan, active workflow run link, and verification commitment state.
- The Electron main process starts a stoppable scheduled-task worker after app readiness; it runs an initial restart scan, repeats due scans on a bounded interval, reuses the same approval-gated workflow runtime, records worker status telemetry, and mirrors started runs into the background task queue without bypassing Approval Center.
- Skills Square shows scheduler worker status telemetry including enabled/running state, next scan, and last scan counts including reconnected monitor workflows. Blocked monitor definitions expose a Resume action that re-enables the monitor and schedules it for the next due scan.
- Due scheduled monitor scans now persist `activeWorkflowRunId` / status metadata on the monitor definition. If a later scan finds that active workflow run still running, restart-recovered, or waiting in Approval Center, it reports the monitor as reconnected instead of starting a duplicate run; if the active run is blocked, the monitor is blocked with the run detail; if the run is complete or missing, the stale link is cleared before the next dispatch.

- The Approval Center navigation item shows the current shared execution-policy matrix for chat, browser, workspace, terminal, git, workflow, network, and external-service actions.
- Git commit approvals require staged-file scope, unstaged-change risk, and test-commitment confirmation before the Approve action becomes available.
- Browser-use task approvals are indexed in the main process, mirrored into a unified pending-approval queue, exposed as a pending approval snapshot, streamed into Approval Center, and routed through unified approve/reject IPC while keeping the browser-specific approval API compatible.
- Agent-proposed terminal commands now use `requestShellCommandApproval`; confirm mode queues a `shell.command` request in Approval Center and the main process writes to the target terminal only after the matching approval is accepted. Auto mode executes immediately through the same policy path.
- Files panel stage/revert file and hunk actions now enter the unified Approval Center in confirm mode and execute from the main process only after approval.
- Git, workflow, network, and connector producers have a typed `proposeApproval` bridge that evaluates the shared execution policy before either blocking, allowing, or queuing the proposal in the unified Approval Center list; git commit now also has a concrete `requestGitCommitApproval` producer fed by `/commit` staged-diff preflight.
- Channels now exposes a typed channel adapter abstraction through the main/preload bridge and renderer, with staged entries for mobile chat, Slack, GitHub, Docs, Calendar, Database, voice input, and the existing file/image input path. ## Current Agent Workflow Slice

Design: enforce the shared execution policy at the privileged IPC boundary, while routing explicit side-effect proposals through the Approval Center when the policy requires confirmation. Agent-proposed shell commands, Files panel workspace stage/revert actions, `/commit <message>` git commits, approval-required workflow run recipes, fork queue-start requests, and fork merge-back/discard lifecycle actions enter Approval Center first and execute only after approval. `/commit` now runs a read-only staged-diff preflight before queuing approval, so empty staged commits are blocked and Approval Center receives the same staged files, grouped file review, diff size, unstaged-change risk, test commitment, and latest terminal test/verification result shown in chat; the Approve action is gated until staged-file scope, unstaged-change risk, and test commitment are locally confirmed. `plan_mode` maps to `read_only`, so the same paths are blocked when the user is planning or the workspace is untrusted. Slash command mode actions are held as first-class chat adapter state, displayed in the composer, sent with the next model request as explicit runtime metadata, and consumed by the legacy Python SSE gateway as whitelisted backend task guidance; `/fork <intent>` additionally asks the main process to prepare an isolated branch-backed Git worktree under the desktop data directory, creates a local `agent_run` fork thread pointing at that worktree, persists source/worktree/branch/base metadata with an active lifecycle state, reports source dirty-state risk, switches the app to it without sharing the source workspace, exposes copyable fork details from the thread menu for lifecycle review, and routes merge-back/discard requests through Approval Center before executing clean-worktree merge-back or desktop-managed worktree cleanup. `/fork queue <task1; task2>` marks each fork thread with queue group/index/status metadata, supports optional `@agent` prefixes per subtask for dispatch assignment, queues `fork.queue_start` approval before the queue can move from waiting to ready, and refreshes thread state to `ready` or `blocked` after the Approval Center decision; `/fork dispatch` is the explicit later step that starts approved ready subtasks as agent runs inside their isolated worktrees and records running/completed/blocked queue states. Merge conflicts and dirty worktrees keep the fork in `merge_pending` with a lifecycle message; successful merge records `merged` and marks branch cleanup pending, and successful cleanup records `closed` plus branch cleanup status.
