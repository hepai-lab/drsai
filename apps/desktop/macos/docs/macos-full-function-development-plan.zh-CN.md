## 0. 计划总览（N 个模块 / M 个功能点）

本计划固定为 **N=12 个模块、M=72 个功能点**，每个模块包含 6 个可独立追踪、实现和验收的功能点。`MOD-xx` 是交付分组，`Fxx.y` 是需求、代码、测试、缺陷和发布证据的唯一追踪键。

N、M 不是估算值，而是发布范围常量：

- `N = macosFeatureModules.length = 12`；一个模块代表一个可独立燃尽和验收的产品域。
- `M = Σ module.features.length = 72`；一个功能点代表一项必须拥有独立需求、测试映射和证据状态的最小发布能力。
- 机器可读唯一真源为 `apps/desktop/shared/test-kit/macosFeatureCatalog.mjs`；本文负责说明范围和执行策略，CI 负责阻止文档、清单和实际测试发生漂移。
- 当前清单将 72 个功能点映射到 **62 个独立自动化 suite**；任何 suite 失败、跳过、未执行或执行收据不属于当前源码指纹，关联功能点均不得进入 `accepted`。

进度采用两个维度，禁止混用：

- **实现状态**：`未开始 / 开发中 / implemented / capability-gated`，由代码、L0～L3 自动化和 inventory 证明。
- **验收状态**：`未验收 / 部分通过 / accepted`，只有该功能点要求的全部门禁通过并归档证据后才可为 `accepted`。
- 总完成数只统计 `accepted`；在没有 macOS 设备或 macOS CI 证据时，涉及 L4～L6 的功能点即使已经 `implemented`，也不得计入完成数。

## 1. 当前状态与结论

macOS 端已经具备 Electron 产品壳、共享 renderer/preload、持续扩展的 shared main 服务，以及登录、基础 Chat/Agent、线程、工作区、文件、Git、PTY、诊断、Interactive Debugger、串行语音、Runtime 安装和更新框架。它适合作为继续开发的基线，但还不是公开测试版或正式版：

- 当前 inventory 为 preload 264、Windows 264、macOS 264，macOS IPC 接线覆盖率为 100%，缺口为 0。该数字只证明共享 UI 到平台 main 的通道完整，不代表真机功能或发布门禁已经通过。
- macOS handler 已由统一安全 registrar 覆盖来源校验、传输结构、错误脱敏、超时、取消、幂等和审计；后续新增 handler 必须继续通过同一契约，禁止退回裸注册。
- 共享 preload 暴露完整 API，平台 capability/inventory 负责阻止运行条件不满足的入口；Browser、Remote、MCP 等通道均已接线，但仍必须通过各自 readiness、凭据、Runtime 和审批门禁，Debugger 仅允许显式环境开关启用。
- 应用生命周期、Keychain、TCC、睡眠唤醒和崩溃恢复已有 fake-platform/contract 实现与测试；其真实 Apple 平台行为，以及 Browser Chromium、原生模块、签名和更新链，仍缺 L4～L6 证据。
- `electron-builder.yml` 引用的两个 entitlement 文件目前缺失，且根 `.gitignore` 的 `build/` 规则会忽略它们。
- `verify` 在 `build` 前要求 `out/**`，干净 checkout 的验证顺序不成立；现有不少测试还是源码字符串断言。
- Windows 跨主机 `typecheck/build` 可作为静态基线，但不能替代真实 macOS 上的 Keychain、TCC、PTY、Apple Silicon、签名、公证、安装和升级验收。

L1 覆盖率范围由 `macosCoveragePolicy.mjs` 固定，禁止在 CI 中临时排除低覆盖文件：`sharedBusinessSources` 当前包含 51 个无 Electron/OS 依赖的共享领域服务，统计行覆盖；`coreStateMachineSources` 是其中 15 个具有持久化状态转换、审批/owner 决策或重启恢复语义的高风险状态机，统计分支覆盖；`integrationAdapterSources` 对超大平台/格式 adapter 单独统计行覆盖，当前包含 `channelAdapters.ts`。`verify:coverage` 必须在同一源码指纹下实际运行全部 61 个功能 suite、生成 c8 原始结果，再由独立验证器聚合并签发 `build/acceptance/coverage/shared-business-summary.json`。收据必须绑定精确范围、每个范围源码、原始 c8 报告和 61-suite 执行收据的 SHA-256；验收器逐项重算，并以真实篡改测试证明 fail-closed。收据缺失、源码指纹过期、范围文件缺失、任一 suite 跳过，或共享业务行低于 80%、核心状态机分支低于 90%、集成 adapter 行低于 55%，均阻断 72 点验收。

测试必须使用固定 seed、fake clock、隔离临时目录和唯一 Keychain service 名；失败时上传日志、截图、视频、trace、进程树和应用数据快照，秘密必须先脱敏。

MOD-10 中 F10.5 的“恰好一次”必须由自动化测试逐项证明，不得用单次成功运行代替。`suite:scheduled-tasks` 至少包含以下验收场景：

1. 使用 fake clock 固定 `scheduledFor`，两次并发 `run-due` 只能产生一个 `triggerKey` 和一个 Workflow run。
2. App 休眠跨过多个周期后只补偿一次，并把 `nextRunAt` 推进到 fake clock 当前时间之后；审计记录保留原计划时间、补偿时间和 missed-run policy。
3. 高风险 Workflow 第一次扫描只生成一个稳定审批项，不创建运行、不推进到期时间；审批未决时重复扫描不得重复排队。
4. 批准后重新扫描只启动一个运行并推进 `nextRunAt`；拒绝、过期或模板失效必须显式 blocked/skipped，不能记为成功。
5. 已有 `running` 或 `waiting_approval` 运行时，重启和唤醒扫描只能重连同一 run；不得重放 terminal、external 或其他副作用步骤。
6. 单个任务 prepare/start 失败不能中断同批其他到期任务；失败任务保留原到期键和可诊断历史，重试成功后仍只生成一个 run。
7. 在持久化写入失败、损坏主文件和备份恢复夹具下，不能出现“Workflow 已启动但调度状态回滚后再次启动”的静默重复；无法证明原子提交时必须 fail-closed 并进入人工恢复状态。
8. 删除任务只取消未来触发，已产生的审批、Workflow run、后台任务和审计历史继续可查询。

其中 1～6 在 L1/L2 使用隔离临时目录、fake clock 和 fake Workflow runtime 每次 PR 执行；5、7 在 macOS arm64 packaged App 做强制退出/重启与睡眠唤醒故障注入；8 同时校验 Workflow 与后台任务存储。任一用例失败、跳过或缺少与当前 commit 绑定的收据，F10.5 保持 `partial`。

### 3.3 功能点级验收规则

每个 `Fxx.y` 必须在测试清单中登记以下字段：`featureId`、需求说明、owner、capability、IPC/API、正向用例、权限/非法输入用例、取消/超时用例、重启恢复用例、适用平台和证据链接。验收规则如下：

1. 功能代码、测试和 inventory 状态在同一 PR 更新。
2. 至少一条正向自动化用例；涉及输入或权限时至少一条负向用例。
3. 涉及长任务时必须覆盖取消、超时和重复调用；涉及持久化时必须覆盖重启恢复和迁移。
4. 涉及平台 adapter 时，先通过 fake port contract，再通过真实 macOS integration。
5. 标记 `capability-gated` 只能作为阶段性状态：UI 必须不可触发，并有目标里程碑和 owner。
6. flaky 测试不得简单重跑后放行；7 天滚动 flaky rate 必须低于 0.5%，否则阻断 RC。

### 3.4 功能点自动化验收登记表

每个 `Fxx.y` 必须在测试清单中登记一行；不能仅用模块级测试结果代替功能点证据。建议将机器可读清单维护为 `macos-feature-acceptance.json`，由 CI 校验字段完整性、测试结果和证据链接。

| 字段 | 必填内容 | 自动判定规则 |
|---|---|---|
| `featureId` | `F01.1`～`F12.6` 中的唯一编号 | 72 个编号无缺失、无重复 |
| `moduleId` | 所属 `MOD-01`～`MOD-12` | 与功能点前缀一致 |
| `implementationStatus` | `not_started/in_progress/implemented/capability_gated` | `implemented` 必须关联代码与 L0～L3 结果 |
| `acceptanceStatus` | `not_tested/partial/accepted` | 仅全部适用门禁成功时允许 `accepted` |
| `testIds` | 正向、负向及适用的取消/超时/恢复用例 | 不得为空；高风险功能必须含拒绝用例 |
| `testEvidence` | suite 行为类别、测试入口、源码/定义/输出 SHA-256 | 必须与当前 suite 清单和磁盘测试源码精确一致；任一漂移失败关闭 |
| `requiredLevels` | L0～L6 的适用集合 | 不得低于 3.2 的模块最低门禁 |
| `evidence` | CI run、报告、日志、截图、产物哈希 | 每条可访问且绑定 commit SHA、平台和时间 |
| `owner` | 责任人或团队 | 不得为空 |

单个功能点的自动验收算法如下：

1. CI 校验功能清单恰好包含 72 个合法且唯一的 `featureId`。
2. 执行该功能点声明的全部 `testIds`；任一失败、跳过或无结果，状态均不得为 `accepted`。
   每张执行收据还必须绑定规范测试入口、入口源码 SHA-256、suite 定义 SHA-256、输出 SHA-256 与实际 `aspects`；CI 必须从当前清单和磁盘源码重算，不能只信任收据自报字段或外层文件哈希。
3. 涉及输入、路径、权限或外部命令时，必须同时通过正向与拒绝/非法输入用例。
4. 涉及异步长任务时，必须通过成功、失败、取消、超时、重复请求和重启恢复用例。
5. 涉及持久化或迁移时，必须在全新数据、旧版本数据、损坏数据和部分写入四种夹具下验证原子性与可恢复性。
6. 要求 L4～L6 时，证据必须来自 macOS arm64；Windows/Linux fake 测试只能证明共享逻辑，不能替代平台验收。
7. CI 根据测试报告回写候选状态；人工只审核证据真实性和平台例外，不得手工绕过失败门禁。

功能点通过标准统一为：**所有必需测试成功 + 无跳过 + 无未关闭 P0/P1 缺陷 + capability 与 inventory 一致 + 证据已归档**。模块通过标准为其 6 个功能点全部 `accepted`；产品完成标准为 12 个模块、72 个功能点全部通过。

### 3.5 自动化判定与验收输出

验收分为三层，CI 不允许用上层汇总结果掩盖下层缺失：

| 判定层级 | 输入 | 自动化通过条件 | 输出 |
|---|---|---|---|
| 功能点（M=72） | `featureId`、`testIds`、`requiredLevels`、capability、inventory、缺陷与证据 | 声明的测试全部成功且无 skip；适用 L0～L6 全通过；P0/P1 为 0；代码、capability 与 inventory 一致；证据绑定 commit SHA | `accepted` 或明确的未通过原因 |
| 模块（N=12） | 每个模块固定 6 个功能点 | 6/6 功能点均为 `accepted`；任一点 partial/failed/skipped 均阻断模块 | `MOD-xx: accepted` 与 6 条证据索引 |
| 产品/发布 | 12 个模块、核心旅程、发布产物 | 12/12 模块、72/72 功能点通过；L0～L6 适用门禁通过；P0/P1=0；Windows 回归门禁通过 | 可发布结论、SBOM、provenance、哈希和回滚证据 |

CI 必须生成机器可读的 `macos-feature-acceptance.json` 和人类可读汇总报告。报告至少显示：`accepted/partial/not_tested` 数量、每模块 6 点燃尽、失败测试、跳过测试、缺失证据、inventory 差异、P0/P1 缺陷和产物哈希。任何字段缺失、测试被跳过、证据不属于当前 commit，流水线均失败。

在当前无 Mac 的条件下，执行规则为：Windows/Node 环境负责 L0～L3，结果最多把功能点推进到 `implemented` 或 `partial`；需要 L4～L6 的功能点必须等待 macOS arm64 CI 或真实 Mac 证据，禁止人工改写为 `accepted`。R51 已取得 L0～L3 与工作区指纹绑定的 P0/P1=0 证据；当前仍因工作区不是 clean commit，且多数功能点要求 Apple 平台层级，严格发布验收数为 **0/72 accepted、72/72 partial**。此前的 **20/72** 表示早期“实现完成”计数，不符合本节 `accepted` 定义，不再作为发布完成数使用。

### 3.6 CI 流水线与建议命令

当前仓库的稳定验收入口如下；均从 `apps/desktop` 执行：

```text
npm ci

npm run verify:contract --workspace opendrsai-macos-desktop
npm run verify:inventory --workspace opendrsai-macos-desktop
npm run verify:renderer-l3 --workspace opendrsai-macos-desktop
npm run verify:coverage --workspace opendrsai-macos-desktop
npm run verify:defects --workspace opendrsai-macos-desktop
npm run verify:platform-evidence --workspace opendrsai-macos-desktop
npm run verify:acceptance --workspace opendrsai-macos-desktop
npm run verify --workspace opendrsai-macos-desktop
```

在 macOS arm64 环境继续执行 `build:mac:dir`、`verify:packaged`、`verify:packaged:l5`；RC 环境执行 `verify:release:l6-auto`、`verify:tcc:l6`、`verify:online-update:l6`，再分别用 `record:l4-evidence`、`record:l5-evidence`、`record:l6-evidence` 归档与当前 commit 和产物哈希绑定的证据。任何记录命令都不能把失败结果提升为通过。

- **PR-fast（全平台）**：L0-L3，目标 15 分钟内完成。
- **PR-mac（macOS arm64）**：L4 和 build，涉及 `shared/**`、`macos/**`、依赖或构建配置时必跑。
- **Nightly**：L5、故障注入、重复启动/退出 100 次、2 小时稳定性。
- **RC**：L6、更新矩阵、24 小时稳定性、完整证据归档；失败不得发布。
- 所有共享层改动还必须通过 Windows 全量发布门禁，避免共享抽取破坏现有 Windows 产品。

### 3.7 核心自动化用户旅程

以下旅程在 packaged App 中执行，均需验证成功、失败、取消和重启恢复：

1. 首次启动 → Runtime 安装 → 登录 → Gateway 就绪 → Chat → Agent → 重启恢复。
2. 创建 Workspace → 浏览/编辑文件 → Git diff/stage → checkpoint → restore。
3. Terminal 创建 → 输入 → resize → 后台/唤醒 → kill → App 退出无残留。
4. 高风险操作 → 审批 → 允许/拒绝 → 审计记录 → 重启后状态一致。
5. Browser → Debugger → MCP 工具调用 → 分别取消并检查资源回收。
6. SSH host key 审批 → 远程 Workspace/PTY/Agent → 断网 → 重连恢复。
7. Workflow/计划任务 → App 重启或睡眠 → 恰好一次补偿执行。
8. 分享/渠道/语音/通知 → 撤权或拒权 → 安全降级与正确任务路由。
9. 安装旧签名版 → 在线更新 → 健康确认；注入坏版本 → 自动回滚。

## 5. 完成定义（Definition of Done）

macOS “全部完整功能完成”必须同时满足：

- 12 个模块、72 个功能点全部为 `implemented`；经产品确认的平台例外必须有 ADR、capability gating 和自动化测试。
- Desktop API inventory 覆盖率 100%，不存在 renderer 可触发但 main 未注册的 handler。
- 共享业务、平台 port、macOS adapter 分层完成，Windows/macOS 不复制大段业务 handler。
- L0-L6 全部门禁通过；P0/P1 用户旅程通过率 100%；核心状态机分支覆盖率 ≥90%；flaky rate <0.5%。
- Runtime 可复现、可验证、可取消、可修复；退出后 Gateway/PTY/辅助进程残留为 0。
- Keychain、TCC、通知、菜单、Dock、deep link、睡眠唤醒和无障碍经过真实 Apple Silicon 验收。
